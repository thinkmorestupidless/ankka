- https://kotlinlang.org/docs/coroutines-cancellation.html — [cancellation] cooperative cancellation, `yield`/`isActive`/`ensureActive`, rethrow `CancellationException`, `withContext(NonCancellable)` only with `withContext`, `withTimeoutOrNull`, `runInterruptible` for blocking JVM calls.

- https://kotlinlang.org/docs/shared-mutable-state-and-concurrency.html — [shared-state] `@Volatile` does not help, atomics, thread confinement, `Mutex.withLock` suspends rather than blocks.
- https://kotlinlang.org/docs/channels.html — [channels] channels as suspending `BlockingQueue`, `produce`, `close`, fan-in/out, `consumeEach` cancels the channel on failure.
- https://kotlinlang.org/api/kotlinx.coroutines/kotlinx-coroutines-core/kotlinx.coroutines/-global-scope/ — [GlobalScope] delicate API, "an antipattern", replacements, do not replace with `CoroutineScope().launch`, legitimate use requires `@OptIn(DelicateCoroutinesApi::class)` and a `CoroutineExceptionHandler`.
- https://kotlinlang.org/api/kotlinx.coroutines/kotlinx-coroutines-core/kotlinx.coroutines/run-blocking.html — [runBlocking] for `main`, tests and non-suspend callbacks; "Calling runBlocking from a suspend function is redundant" and risks thread starvation; nested `runBlocking` warning.

- https://kotlinlang.org/api/kotlinx.coroutines/kotlinx-coroutines-core/kotlinx.coroutines/-non-cancellable/ — [NonCancellable] designed for `withContext`; `launch(NonCancellable)` severs the parent-child relation; `ensureActive()` after the block.

- https://kotlinlang.org/api/kotlinx.coroutines/kotlinx-coroutines-test/ — [coroutines-test] `runTest` skips delays, 60 s default timeout, uncaught child exceptions rethrown at end, `StandardTestDispatcher` vs `UnconfinedTestDispatcher`, `advanceUntilIdle`/`runCurrent`, `Dispatchers.setMain`/`resetMain`, inject dispatchers or delays are not skipped, `backgroundScope`.

## 2. Detecting the language and flavour

**Files.** `*.kt` is Kotlin source; `*.kts` is a Kotlin script, almost always Gradle build logic (`build.gradle.kts`, `settings.gradle.kts`, `buildSrc/**/*.kt`, `gradle/libs.versions.toml` beside it) [gradle-project] [version-catalogs]. Review `.kts` as build code, not application code.

**JVM server / library.** `plugins { kotlin("jvm") version "2.x.y" }` or `id("org.jetbrains.kotlin.jvm")`; `kotlin { jvmToolchain(21) }` or `compilerOptions { jvmTarget = JvmTarget.JVM_21 }`; dependencies on Ktor/Spring/Exposed/http4k; `src/main/kotlin`, `src/test/kotlin` [gradle-project] [gradle-compiler]. A library adds `explicitApi()` and the BCV plugin or `abiValidation {}` with an `api/*.api` file [explicit-api] [BCV] [whatsnew22].

**Android.** `com.android.application` or `com.android.library` plugin, `android {}` block, `AndroidManifest.xml`, `src/main/res`, imports of `android.*`, `androidx.*`, `viewModelScope`/`lifecycleScope`, `@Composable`. The coroutine rules in this file still apply; UI-thread rules (`Dispatchers.Main`) matter only here [android-coroutines].

**Kotlin Multiplatform.** `kotlin("multiplatform")` plugin; targets declared inside `kotlin {}` (`jvm()`, `iosArm64()`, `androidTarget()`, `js()`, `wasmJs()`); directories `src/commonMain`, `src/commonTest`, `src/<target>Main`, intermediate sets like `appleMain`/`iosMain`; `expect`/`actual` declarations [kmp]. In common code, `sealed` hierarchies declared `expect` still need `else` in `when` [sealed]; JVM-only annotations (`@JvmStatic`, `@JvmInline` is fine, `@Throws` is multiplatform) and `java.*` imports do not belong in `commonMain`.

**Tooling the reviewer should glance at before flagging anything:**
- `.editorconfig` with `ktlint_*` keys, a `ktlint` Gradle plugin (`org.jlleitschuh.gradle.ktlint`, `com.pinterest.ktlint`) or a pre-commit hook: formatting, import ordering, naming are then enforced; skip them [ktlint].
- `detekt.yml` / `config/detekt/detekt.yml` and the `io.gitlab.arturbosch.detekt` plugin: look at which rule sets are active and whether `buildUponDefaultConfig` is set. Items below marked "detekt: active" are already caught when detekt runs in CI [detekt-*].
- `explicitApi()` / `explicitApiWarning()` or `-Xexplicit-api=strict` in `compilerOptions`: visibility and return types on public declarations are compiler-enforced [explicit-api].
- `allWarningsAsErrors = true`, `extraWarnings = true`, `progressiveMode = true` in `compilerOptions {}`: compiler warnings (unused, deprecated, redundant modifiers, platform-type exposure warnings under `-Xjspecify-annotations=strict`) are already blocking [gradle-compiler] [java-interop].
- `api/*.api` or `*.klib.api` files: binary compatibility is checked; a PR that changes them is an API change by construction [BCV].
- `kotlinx.coroutines.debug` or `-Dkotlinx.coroutines.debug` in test config: unrelated to review, ignore.
- Which test stack: `junit-jupiter` + `mockk` + `kotlinx-coroutines-test` + `turbine`, or `kotest-runner-junit5` + `kotest-assertions`. The Tests section splits on this.

## 3. Checklist

Format: **Rule.** signal → why. [source]. "detekt: X (active/inactive)" names the rule that would catch it.

### Null safety

- **No `!!` in production code without a comment proving the invariant.** Grep `!!` outside `src/test`. It converts a design gap into an NPE at a distance; the compiler offers `?.`, `?:`, `requireNotNull`, smart casts. Android Lint has `AvoidUsingNotNullOperator`; detekt `UnsafeCallOnNullableType` (active). [null-safety] [detekt-bugs] [android-lint]
- **`map[key]!!` is a `MapGetWithNotNullAssertionOperator` smell.** Use `getValue(key)` (throws with the key in the message), `getOrElse`, or make absence a handled case. detekt active. [detekt-bugs]
- **Platform types must not leak.** A `public`/`internal` function or property whose type is inferred from a Java call (`val x = javaObj.getFoo()`, `fun f() = javaList[0]`) must declare its Kotlin type explicitly, choosing `T` or `T?` deliberately. "A public function/method returning an expression of a platform type must declare its Kotlin type explicitly." detekt `HasPlatformType` (active). [coding-conventions] [java-interop] [detekt-bugs]
- **Decide nullability at the Java boundary, once.** When a Java API is unannotated, the Kotlin wrapper is the place to write `: Foo?` and handle it; downstream code should never see `Foo!`. Check whether the Java library ships JSpecify/JetBrains/JSR-305 annotations; if it does, prefer `-Xjspecify-annotations=strict` so mismatches are errors rather than warnings. [java-interop] [j2k-null]
- **`lateinit` only for framework/DI/test-setup injection, never as a lazy initialisation shortcut.** Grep `lateinit var`. Access before init throws `UninitializedPropertyAccessException`; a nullable type, `by lazy`, or a constructor parameter is usually the honest model. `lateinit` on a type that could be a primitive is a compile error anyway. detekt `LateinitUsage` (inactive by default; enable for libraries). [properties] [detekt-bugs]
- **`?.let { } ?: run { }` chains hiding control flow.** A `?.let` whose lambda has side effects, or an Elvis after `let` where the lambda can itself return null, reads as "if not null … else" but is not (a `let` that returns `null` falls into the `?:` branch). Prefer `if (x != null) … else …` for binary conditions. [coding-conventions] [scope-functions]
- **Elvis with `throw`/`return` is the idiom for "must be present".** `val name = node.name ?: throw IllegalArgumentException("name expected")` or `?: return null`; prefer `requireNotNull(x) { "…" }` / `checkNotNull(x) { "…" }` which smart-cast and carry a message. detekt `UseRequireNotNull`/`UseCheckNotNull` (active). [null-safety] [idioms] [detekt-style]
- **Smart casts do not work on `var` properties or `open`/custom-getter `val`s.** A reviewer who sees `if (this.foo != null) use(foo!!)` on a mutable property should ask for a local copy (`val foo = foo ?: return`) rather than `!!`; the `!!` is there because the compiler is right that another thread may have changed it. detekt `NullCheckOnMutableProperty` (inactive). [typecasts] [detekt-bugs]
- **`List<T?>` versus `List<T>?` versus `List<T?>?`.** Each means something different; a nullable collection usually should be empty instead (`orEmpty()`), and a collection of nullables should be filtered at the boundary (`filterNotNull()`), not re-checked at every use. detekt `UseOrEmpty` (active). [null-safety] [detekt-style]
- **`Any?` parameters or returns are a type-system opt-out.** Flag `Any?` (or `Any`) in a signature unless the function is genuinely generic over everything (logging, serialisation). Ask for a sealed type, a generic parameter, or an interface. [api-readability]
- **Prefer `firstOrNull()`, `getOrNull()`, `maxOrNull()`, `toIntOrNull()` to their throwing twins when the empty/invalid case is normal.** `first()` on a possibly empty list is a `NoSuchElementException` waiting for production data. [j2k-null] [idioms]
- **`as` where `as?` was meant, and `as T?` which still throws.** `x as String?` throws `ClassCastException` if `x` is an `Int`; `x as? String` returns null. detekt `CastToNullableType` (inactive), `SafeCast` (active), `UnsafeCast` (active, for casts that can never succeed). [typecasts] [detekt-bugs] [detekt-style]
- **Nullable `Boolean` in a condition must compare explicitly.** `if (flag == true)` / `if (flag == false)`, never `if (flag!!)` or `if (flag ?: false)` without a reason. [coding-conventions]
- **`toString()` or string templates on a nullable.** `"id=$id"` with `id: Long?` silently prints `"null"`. detekt `NullableToStringCall` (inactive). [detekt-bugs]

### Idioms and language features

- **`val` by default; `var` only when reassigned.** "Always declare local variables and properties as `val` rather than `var` if they are not modified after initialization." detekt `VarCouldBeVal` (active). [coding-conventions] [detekt-style]
- **Default parameter values instead of overloads; factory functions instead of constructor telescoping.** A new overload that only supplies a default is a smell unless `@JvmOverloads` is deliberately absent for Java callers. [coding-conventions]
- **Named arguments for several same-type parameters and for every `Boolean` argument.** `draw(10, 10, 100, 100, true)` → `draw(x = 10, y = 10, width = 100, height = 100, fill = true)`. For a *library*, do not take a `Boolean` parameter at all: split the function or use an enum. detekt `NamedArguments` (inactive), `UnnamedParameterUse` (inactive). [coding-conventions] [api-readability] [detekt-complexity]
- **`if` for two branches, `when` for three or more, both as expressions where possible.** `when (x) { true -> …; false -> … }` or `if/else if/else if` chains are the wrong tool. detekt `UseIfInsteadOfWhen`. [coding-conventions]
- **Scope functions: pick by the table, do not nest, do not chain confusingly.** `apply` configures and returns the receiver; `also` for side effects; `let` for a nullable or to introduce a local; `run`/`with` for grouping calls and computing a result. "Avoid nesting scope functions … it's easy to get confused about the current context object." Nested `this`/`it` is a correctness hazard, not just taste. detekt `NestedScopeFunctions` (inactive), `UnnecessaryApply`/`UnnecessaryLet` (active). [scope-functions] [detekt-complexity] [detekt-style]
- **`lazy` thread-safety mode must match the use.** Default is SYNCHRONIZED; `LazyThreadSafetyMode.NONE` is only right when initialisation and use are provably on one thread; `PUBLICATION` when the initialiser is idempotent. A `by lazy(NONE)` on a shared object is a race. [delegation]
- **Extension functions: restrict visibility; dispatch is static.** "Restrict the visibility of extension functions as much as it makes sense." A `public` extension on `String`/`Any`/`List<*>` in a shared module pollutes every caller's completion list. Remember an extension on a supertype is chosen by the *declared* type, and a member with the same signature always wins, so an extension that "overrides" a member does nothing. [coding-conventions] [extensions] [android-lint MemberExtensionConflict]
- **`inline` only for functions taking lambdas or needing `reified`.** `inline` on a function with no lambda parameter produces the `NOTHING_TO_INLINE` warning and is usually noise; large inline functions bloat every call site; a `public inline` body may only reference public or `@PublishedApi internal` declarations, and that body is copied into consumers, so changing it later is a binary-compat concern. [inline] [api-compat]
- **`operator` and `infix` sparingly.** `infix` only for two operands "which play a similar role" (`to`, `and`, `zip`), never for something that mutates the receiver; `operator fun plus` that does not behave like addition is a trap. [coding-conventions]
- **Destructuring is positional.** `val (email, username) = user` silently swaps if the data class reorders its properties. Avoid destructuring data classes with more than two or three properties and never across a module boundary; use `_` for ignored components. The name-based form (`val (mail = email) = user`, `-Xname-based-destructuring`) is the fix when the project has enabled it. detekt `DestructuringDeclarationWithTooManyEntries` (active, max 3). [destructuring] [detekt-style]
- **`Pair`/`Triple` in signatures are a missing data class.** "Named data classes are usually better because their property names make code easier to read." Fine locally or in `associate { a to b }`; flag them as parameter or return types. Note `associate` allocates a `Pair` per element; `associateBy`/`associateWith` do not. [data-classes] [transformations]
- **String templates over concatenation; raw strings with `trimIndent`/`trimMargin` over `\n`; no braces around a simple variable (`"$name"`, not `"${name}"`).** Also prefer stdlib helpers (`ifBlank`, `substringAfter`, `removeSurrounding`, `joinToString`, `buildString`) over index arithmetic or regex. [coding-conventions] [j2k-strings]
- **`const val` for compile-time constants in top-level or `object` scope; `val` + `@JvmField` otherwise.** A top-level `val X = "literal"` is a getter call from Java and cannot be used in annotations. detekt `MayBeConstant` (active). [properties] [detekt-style]
- **`typealias` versus `value class` versus `fun interface`.** A typealias is "just a name": `typealias UserId = String` accepts any `String`. Use `@JvmInline value class UserId(val value: String)` for a real type; use a plain functional type or typealias for "any function with this shape", a `fun interface` when the thing has a contract beyond its signature. [value-classes] [fun-interface]
- **`TODO()` left in the diff.** It returns `Nothing` and throws `NotImplementedError` at runtime, so it compiles anywhere. Any `TODO(` in non-test, non-WIP code is blocking. detekt `NotImplementedDeclaration` (inactive), `ForbiddenComment` for `TODO:`/`FIXME:` comments (active). [idioms] [detekt-exceptions] [detekt-style]
- **Trailing lambdas and SAM conversions: ambiguity needs an explicit adapter.** `executor.execute { }` is fine; when two overloads take different SAM types, write `Runnable { }`. Only Java *interfaces* SAM-convert, not abstract classes. Android Lint `LambdaLast`, `ImplicitSamInstance`. [java-interop] [android-lint]
- **Prefer a property to a function when it does not throw, is cheap or cached, and is pure given the object's state**; otherwise a function. A `val size get() = fetchFromDb()` violates every one of those. [coding-conventions]
- **`..<` for open-ended ranges, `for` over `forEach` on a range or plain collection.** `0..n - 1` and `(0 until n).forEach {}` are both flagged; detekt `ForEachOnRange` (active), `RangeUntilInsteadOfRangeTo` (inactive). [coding-conventions] [detekt-performance]
- **Labeled returns: at most one, never on the last statement of a lambda.** [coding-conventions]

### Classes, data and sealed hierarchies

- **Data classes should be immutable: `val` properties, no `var`.** A `var` in a data class changes `hashCode` after insertion into a `HashSet`/`HashMap` key, breaks `StateFlow` equality-based conflation, and makes `copy()` misleading. detekt `DataClassShouldBeImmutable` (inactive; worth enabling). [data-classes] [StateFlow] [detekt-style]
- **No arrays in data classes without hand-written `equals`/`hashCode`.** Generated `equals` compares arrays by reference ("`==` … check whether the assigned variables point to the same object"); two structurally equal instances are unequal. Ask for `List`, or `contentEquals` in an explicit `equals` plus `contentHashCode`. [arrays] [equality]
- **Only primary-constructor properties take part in `equals`/`hashCode`/`toString`/`copy`.** A property declared in the body (`data class P(val name: String) { var age = 0 }`) is invisible to all of them; `copy()` is shallow, so a `MutableList` property is shared between copies. [data-classes]
- **Data classes are not public library API.** Adding a property changes the generated constructor and `copy` signatures (binary break); reordering changes `componentN` (behavioural break). For a library, a plain class with explicit `equals`/`hashCode`/`toString` and a builder or factory. [api-compat] [api-debuggability]
- **Override `hashCode` whenever `equals` is overridden; `equals` takes `Any?`.** detekt `EqualsWithHashCodeExist`, `WrongEqualsTypeParameter` (active). [equality] [detekt-bugs]
- **Sealed hierarchy + `when` without `else`.** Adding `else` to a `when` over a sealed type or enum "defeats" the compiler's exhaustiveness check: a new subtype will fall into `else` silently instead of failing to compile. Flag `else ->` in such a `when`; the idiomatic form lists every case. detekt `ElseCaseInsteadOfExhaustiveWhen` (inactive; enable it). [sealed] [api-predictability] [detekt-bugs]
- **`sealed interface` over `sealed class` when no shared state; `sealed` over `enum` when variants carry different data; `enum` when each variant is a singleton.** An enum can implement a sealed interface but cannot extend a sealed class. Direct subclasses must live in the same package and module; a non-sealed direct subclass reopens the hierarchy. [sealed] [enums]
- **Singleton sealed variants should be `data object`, not `object`.** `data object Loading : State` gets a readable `toString()`; compare data objects with `==`, never `===`. [objects]
- **`object` initialisation is lazy on first access and thread-safe; companion initialisation happens on class load.** Heavy work in an `object` initialiser runs at an unexpected moment and failures surface as `ExceptionInInitializerError`. [objects]
- **Companion object members are instance members unless `@JvmStatic`.** From Java they are `Foo.Companion.bar()`; constants need `const val` or `@JvmField`. Only relevant if Java calls the class. [objects] [kotlin-from-java]
- **`value class` for ids and units; watch the boxing boundaries.** It boxes when used as a generic argument, through an interface, or as a nullable (`Foo?`), so a `List<UserId>` allocates like a `List<Wrapper>`. `===` on value classes is a compile error. Mangled method names need `@JvmName` or `@JvmExposeBoxed` for Java callers. [value-classes] [kotlin-from-java]
- **Delegation `by` for interface forwarding, not inheritance.** `class Logged(private val inner: Repo) : Repo by inner` is the idiom; an `open class` with `override` of every method to add one behaviour is not. Kotlin classes are `final` by default; a new `open` needs a reason, and `protected` in a final class is meaningless. detekt `ProtectedMemberInFinalClass` (active). [detekt-style]
- **Exceptions are classes, never `object`s.** An `object MyError : Exception()` shares one stack trace across every throw. detekt `ObjectExtendsThrowable` (inactive). [exceptions] [detekt-exceptions]
- **Explicit backing fields and backing properties.** `private val _items = mutableListOf<T>(); val items: List<T> get() = _items` is the pattern; `val items: List<T> field = mutableListOf()` is the newer explicit-backing-field form. Either way, the public type must be read-only. [properties]

### Collections and sequences

- **Expose read-only types; keep mutability private.** `MutableList`, `MutableMap`, `MutableStateFlow`, `ArrayList` in a public signature is a defect unless mutation is the point. Return `List`/`Map`/`Set`, store the mutable one privately. Remember a read-only interface is a *view*: the holder of the mutable reference can still change it under the caller, so for API boundaries copy with `toList()`. [collections] [api-predictability] [android-coroutines]
- **`var` holding a mutable collection is "double mutability".** `var items = mutableListOf<T>()` — choose one: `val` + mutable collection, or `var` + read-only replaced wholesale. detekt `DoubleMutabilityForCollection` (active). [detekt-bugs] [collections]
- **Defensive copies at trust boundaries; `vararg` is already copied.** A constructor storing a `List` parameter directly keeps a reference to the caller's possibly mutable list; `.toList()` it if the class relies on immutability. Arrays passed to or returned from a public API must be copied. [api-predictability]
- **Do not downcast `List` to `MutableList`.** `(items as MutableList).add(x)` works on `ArrayList` and throws `UnsupportedOperationException` on `listOf()`/`List.of()` results; it also violates the declared contract. detekt `DontDowncastCollectionTypes` (inactive). [detekt-bugs]
- **`first()`/`last()`/`single()`/`get(i)`/`getValue()` throw; be sure the collection cannot be empty or the key absent.** Otherwise `firstOrNull()`, `singleOrNull()`, `getOrNull()`, `getOrElse`. [j2k-null] [idioms]
- **`associateBy`/`associateWith`/`toMap` keep the *last* value on key collision.** "If two elements' keys are equal, only the last one remains in the map." When keys may repeat, `groupBy` is the correct call; if uniqueness is an invariant, assert it (`require(map.size == list.size)`). [transformations]
- **`zip` truncates to the shorter list silently.** If the lists must be the same length, check it. [transformations]
- **Long chains over large inputs: `asSequence()`; short chains over small inputs: plain collections.** Each eager step materialises an intermediate list; sequences avoid that and stop early (`take`), but "add some overhead which may be significant when processing smaller collections". A `map { }.filter { }.first { }` over a large list is the classic case for a sequence. detekt `CouldBeSequence` (inactive). [sequences] [detekt-performance]
- **Sorting: `sortedBy`/`sortedWith(compareBy { }.thenBy { })` return copies; `sort*` mutate in place; `reversed()` copies, `asReversed()` is a live view.** The naming convention (`sort` vs `sorted`) is how readers tell mutation apart; a function named `sorted` that mutates is a bug. The docs do not promise stability on the ordering page; the JVM implementation delegates to a stable sort, but do not rely on it in `commonMain` without checking. [ordering] [coding-conventions]
- **Mutable objects as `Set` elements or `Map` keys.** Mutating a key after insertion makes it unfindable; same for `distinct()`/`toSet()` over data classes with `var`s. [equality] [data-classes]
- **Arrays: prefer collections; `IntArray` over `Array<Int>`; `contentEquals`/`contentToString`.** "For most use cases, prefer collections instead." `Array<Int>` boxes every element. detekt `ArrayPrimitive` (active). Spread (`*array`) copies the whole array per call. detekt `SpreadOperator` (active). [arrays] [detekt-performance]
- **Covariance only on read-only types.** A function taking `List<Shape>` accepts a `List<Rectangle>`; one taking `MutableList<Shape>` does not, and an attempt to cast around it is a runtime failure waiting to happen. [collections]
- **`map { }.filterNotNull()` is `mapNotNull { }`; `filter { }.size` is `count { }`; `filter { }.isNotEmpty()` is `any { }`; `flatMap { }.size` is `sumOf { }`.** detekt `UnnecessaryFilter`, `UseAnyOrNoneInsteadOfFind`, `UseSumOfInsteadOfFlatMapSize` (active). [detekt-style]
- **Locale-sensitive operations without a locale.** `"x".uppercase()` is fine (locale-invariant in Kotlin); `String.format(...)`, `toLowerCase()` (deprecated Java-style) and `java.text` formatting without a `Locale` depend on the default locale. detekt `ImplicitDefaultLocale` (active). [detekt-bugs]

### Coroutines and Flow

- **No `GlobalScope`.** "Using GlobalScope to create coroutines is an antipattern." Grep `GlobalScope.`; the only legitimate case is a process-lifetime background task, which then needs `@OptIn(DelicateCoroutinesApi::class)` *and* a `CoroutineExceptionHandler`. Do not accept `CoroutineScope().launch` or `CoroutineScope(Dispatchers.IO).launch` as a replacement: an unowned scope "suffers from all the pitfalls described above". Inject a scope or use `coroutineScope {}`. detekt `GlobalCoroutineUsage` (inactive; enable). [GlobalScope] [dispatchers] [android-coroutines] [detekt-coroutines]
- **Structured concurrency: every `launch`/`async` has an owner whose lifetime matches the work.** A `launch` on a long-lived scope inside a request handler leaks past the request; a `launch` on a request scope for work that must outlive it is cancelled mid-way. Ask "who cancels this and when". For work inside one call, `coroutineScope { }`; for work that must survive the caller, an injected application scope. [dispatchers] [android-coroutines]
- **`runBlocking` only in `main`, tests, and non-suspend callbacks that must call suspend code.** "Calling runBlocking from a suspend function is redundant" and blocks a thread (starvation under a limited dispatcher); nested `runBlocking` can deadlock. Grep `runBlocking` outside tests and `fun main`. [runBlocking]
- **A `suspend` function must not block the thread.** JDBC, `Thread.sleep`, blocking HTTP clients, file IO inside `suspend fun` without `withContext(Dispatchers.IO)` (or an injected IO dispatcher) stalls the dispatcher's threads. Suspend functions should be "safe to call from the main thread": the function doing the blocking is responsible for moving it. `Thread.sleep` in a coroutine should be `delay`. detekt `SleepInsteadOfDelay` (active). For blocking JVM calls that must react to cancellation, wrap in `runInterruptible { }`. [android-coroutines] [cancellation] [detekt-coroutines]
- **Dispatchers: injected, not hard-coded; `Default` for CPU, `IO` for blocking, `Unconfined` never in general code.** Hard-coded `Dispatchers.IO` cannot be swapped for a `TestDispatcher`, so `delay`s inside it are not skipped under `runTest`. Hot paths that only need a view can use `Dispatchers.IO.limitedParallelism(n)`; note `IO` shares threads with `Default`, so `withContext(IO)` from `Default` is cheap. `newSingleThreadContext` must be closed or held globally. detekt `InjectDispatcher` (active). [dispatchers] [Dispatchers.IO] [android-coroutines] [coroutines-test] [detekt-coroutines]
- **Cancellation is cooperative: long loops need `ensureActive()`, `yield()` or `isActive`.** A CPU loop or a loop over blocking calls never observes cancellation otherwise, and `withTimeout` around it does nothing. [cancellation] [android-coroutines]
- **Never swallow `CancellationException`.** `catch (e: Exception)` / `catch (e: Throwable)` / `runCatching { }` around suspending code catches `CancellationException` and breaks propagation: the coroutine keeps running after cancel, and the parent never learns. Fix: `catch (e: CancellationException) { throw e }` before the generic catch, or catch specific types. detekt `SuspendFunSwallowedCancellation` (inactive; enable), `TooGenericExceptionCaught` (active). [cancellation] [android-coroutines] [detekt-coroutines] [detekt-exceptions]
- **Suspending cleanup in `finally` needs `withContext(NonCancellable)`; `NonCancellable` only with `withContext`.** A suspending call in `finally` of a cancelled coroutine throws immediately; `launch(NonCancellable)` "severs" the parent-child relation. After the block, `ensureActive()` before touching anything the cancellation was meant to stop. detekt `SuspendFunInFinallySection` (inactive). [cancellation] [NonCancellable] [detekt-coroutines]
- **`async` without `await` and `async` for fire-and-forget.** An `async` whose `Deferred` is never awaited hides its exception until the scope completes; `launch` is the fire-and-forget builder. Async-style functions (`fun fooAsync(): Deferred<T>`) are "strongly discouraged"; expose `suspend fun foo(): T` and let the caller choose concurrency with `coroutineScope { async { } }`. [async] [coroutine-exceptions]
- **`CoroutineExceptionHandler` only works on root coroutines launched with `launch`, never on children and never on `async`.** A handler installed on a child or on `async` is dead code; the exception propagates to the parent, which is cancelled. `supervisorScope`/`SupervisorJob` make failure one-directional, and then each child must handle its own exceptions (or the handler in the supervisor's scope applies). [coroutine-exceptions]
- **One child's failure cancels the siblings and the parent.** If a batch should continue when one item fails, that is `supervisorScope` or per-item `try/catch` of a *specific* exception, with `CancellationException` rethrown. "The first exception wins"; the rest are attached as suppressed, so logging only `e.message` loses them. [coroutine-exceptions]
- **`suspend fun` returning `Flow` is a contradiction.** Flows are cold; the function should be a plain `fun` that builds the flow, and do its work inside `flow {}` when collected. detekt `SuspendFunWithFlowReturnType` (active), `RedundantSuspendModifier` (active). Likewise a `suspend fun CoroutineScope.foo()` mixes two contexts. detekt `SuspendFunWithCoroutineScopeReceiver` (inactive). [flow-guide] [detekt-coroutines]
- **Inside `flow {}`: no `withContext`, no `launch`, emit from the builder's own coroutine.** Context changes are `flowOn` upstream; concurrent emission is `channelFlow`/`callbackFlow`. Violations are an `IllegalStateException` at runtime, not a compile error. [flow-guide] [Flow-api]
- **Exception transparency: `catch` handles upstream only; never emit from a `catch` block that swallowed a downstream exception; rethrow collector exceptions caught inside the builder.** `try { emit(x) } catch (e: Exception) { emit(fallback) }` violates it and the machinery throws `IllegalStateException` on the next emit. Per-item handling goes in `onEach` before `catch`; `retry`/`retryWhen` for retries. [Flow-api] [flow-guide]
- **`StateFlow` for state, `SharedFlow` for events, `Channel` for point-to-point hand-off.** `StateFlow` conflates and deduplicates by `equals`, so an "event" modelled as `StateFlow<Event>` drops repeats and a mutable object reassigned to itself is not emitted; `SharedFlow` with no subscriber drops the emission (beyond `replay`), so a one-shot event emitted before anyone collects is lost; neither can complete or carry failure. A `Channel` delivers each element to exactly one receiver and can be closed. Read-modify-write on `MutableStateFlow` must be `update { }`, not `value = value + 1`. Expose `asStateFlow()`/`asSharedFlow()`, never the mutable type. [StateFlow] [SharedFlow] [channels] [android-coroutines]
- **Hot flows never complete: every `collect`/`launchIn` on a `StateFlow`/`SharedFlow` must live in a scope that is cancelled.** `shareIn`/`stateIn` keep collecting until their scope dies; `SharingStarted.WhileSubscribed()` is the usual choice when consumers come and go. [SharedFlow] [flow-guide]
- **`Mutex.withLock` in suspending code, `synchronized`/`ReentrantLock` only around non-suspending critical sections.** `synchronized` around a suspend point is a compile error in a lambda and a deadlock in spirit; `@Volatile` does not make `counter++` atomic. Prefer atomics or thread confinement when they fit. [shared-state]
- **Thread-locals do not survive suspension.** Request context, MDC, security context: anything in a `ThreadLocal` read after a suspend point is wrong unless carried as a context element (`asContextElement()`, or the library's `CoroutineContext` element). [dispatchers]
- **`Flow.collect` inside another `collect`, or `collect` where `collectLatest`/`flatMapLatest` was meant.** Nested collection serialises the inner flow and never cancels it on a new outer value; `collectLatest` cancels the previous block. `conflate()` and `buffer()` are explicit back-pressure decisions and should be commented. [flow-guide]
- **`consumeEach` on a shared channel cancels it on the consumer's failure; a plain `for (x in channel)` does not.** Matters in fan-out. [channels]

### Error handling

- **No `catch (e: Exception)` / `catch (e: Throwable)` except at a top-level boundary that logs and rethrows or converts.** Generic catches hide `CancellationException`, `OutOfMemoryError` (for `Throwable`), programming errors. detekt `TooGenericExceptionCaught` (active). [detekt-exceptions] [cancellation]
- **A caught exception must be used: rethrown, wrapped as `cause`, or logged with the exception object.** `catch (e: IOException) { log.warn("failed") }` or `catch (e: X) { return null }` swallows the cause. detekt `SwallowedException` (active); `RethrowCaughtException` (active) for `catch (e) { throw e }` noise; `PrintStackTrace` (active) for `e.printStackTrace()`. [detekt-exceptions] [api-debuggability]
- **`require`/`check`/`error` with a message that names the offending input.** `require(count >= 0) { "Count must be non-negative, was $count" }` for arguments, `check` for state, `error("…")` for unreachable branches. Hand-rolled `if (…) throw IllegalArgumentException(…)` is the same thing with less intent. Do not pass a `Throwable` to `error()`: it stringifies it. detekt `UseRequire`, `UseCheckOrError` (active), `ErrorUsageWithThrowable` (inactive), `ThrowingExceptionsWithoutMessageOrCause` (active). [exceptions] [api-predictability] [detekt-exceptions]
- **`Result<T>` / `runCatching` is not a domain error type.** `runCatching` catches *everything*, including `CancellationException` and `Error`s; a `fun load(): Result<User>` return type is what the KEEP shows as the anti-example: use `User?` when failure carries no information, a sealed result type when it does, and exceptions for failures the caller cannot handle locally. `Result` is for collecting failures to process later (`awaitAll` of many jobs, bulk file reads). A `runCatching { }` whose `onFailure` only logs is a `SwallowedException` with better syntax. [KEEP-Result] [detekt-coroutines SuspendFunSwallowedCancellation]
- **Sealed results versus exceptions: pick one per API and document it.** Libraries should adopt "a consistent approach to exception handling"; wrap third-party exceptions in a library-specific type with the original as `cause` when the dependency is an implementation detail. Mixed APIs (some functions throw, siblings return `null`) are the thing to flag. [api-debuggability]
- **Checked exceptions are invisible in Kotlin.** A Java call that declares `throws IOException` compiles without a `try`; the reviewer must check that the caller handles or documents it, since the compiler will not. Conversely, Kotlin functions called from Java need `@Throws(IOException::class)` or the Java `catch` will not compile. [java-interop] [kotlin-from-java]
- **Never throw from `toString`, `equals`, `hashCode`, `finalize`, or from `finally`; never `return` from `finally`.** detekt `ExceptionRaisedInUnexpectedLocation`, `ThrowingExceptionFromFinally`, `ReturnFromFinally` (active). [detekt-exceptions]
- **Rethrowing a new instance of the same type loses nothing and adds nothing.** `catch (e: IOException) { throw IOException(e) }` — pass it on, or wrap in a *different*, more meaningful type. detekt `ThrowingNewInstanceOfSameException` (active). [detekt-exceptions]
- **`use {}` for every `Closeable`/`AutoCloseable`.** A `try/finally { close() }` is fine but `use` cannot be forgotten. detekt `MissingUseCall` (inactive). [exceptions] [idioms] [detekt-bugs]
- **Custom exceptions with extra constructor arguments should implement `StackTraceRecoverable`** (or offer a `(message, cause)` constructor) so coroutine stack-trace recovery can copy them. Library-grade concern. [api-debuggability]
- **Exceptions types should say what went wrong; data should say where.** `throw RuntimeException("bad")` conveys neither. detekt `TooGenericExceptionThrown` (active). [api-debuggability] [detekt-exceptions]

### Java interop

- **A Kotlin API that Java will call needs `@JvmStatic` on companion functions, `@JvmField`/`const` on constants, `@JvmOverloads` on functions with defaults, `@Throws` for checked exceptions, and `@file:JvmName` on utility files.** Without them Java sees `Foo.Companion.bar()`, `getX()` for constants, only the full-arity signature, and `FooKt`. Only relevant if there *are* Java callers; otherwise these annotations are noise. [kotlin-from-java]
- **`@JvmOverloads` does not protect Kotlin callers' binary compatibility.** Adding a defaulted parameter still removes the old JVM signature for Kotlin call sites; for a library use `@IntroducedAt` (experimental) or hand-written overloads. [api-compat] [kotlin-from-java]
- **`internal` is public bytecode with a mangled name.** Java can call it (`foo$modulename`). It is not an access control against Java consumers; `@JvmSynthetic` or a real `private` is. [kotlin-from-java]
- **Kotlin-only features leaking into a Java-facing API.** Suspend functions (Java sees a `Continuation` parameter), `value class` parameters (mangled names, unboxed types unless `@JvmExposeBoxed`), `Unit`-returning lambdas (Java must `return Unit.INSTANCE`), top-level functions, default arguments, `internal`, `Nothing` in type arguments (raw type in Java), declaration-site variance (`Box<out T>` becomes `Box<? extends T>` only in parameter positions; `@JvmWildcard`/`@JvmSuppressWildcards` to control). Offer a Java-friendly overload or a `CompletableFuture` adapter when Java callers exist. [kotlin-from-java] [value-classes]
- **Interface default methods: know the `-jvm-default` mode.** 2.2 defaults to `enable` (default methods plus `DefaultImpls` bridges); `no-compatibility` breaks binaries compiled against the old scheme. A change to `jvmDefault` in the build is an API-compat change. [kotlin-from-java] [whatsnew22]
- **Nullability annotations on Java APIs you own: add them (JSpecify preferred) so Kotlin sees `T`/`T?` rather than `T!`.** On the consuming side, prefer `-Xjspecify-annotations=strict`. Review a Java PR in a mixed codebase for `@Nullable` on anything that can return null. [java-interop] [j2k-null]
- **`(Mutable)List<T>!` from Java is not read-only.** A Java method returning `List<T>` arrives as a platform collection that Kotlin will happily cast to `MutableList`; declare the Kotlin type you mean and copy if the Java side may mutate it. [java-interop]
- **Java boxed types as type arguments are platform types.** `List<java.lang.Integer>` is `List<Int!>`, so `list[0] + 1` can NPE. [java-interop]
- **Raw and wildcard generics from Java become star/`out` projections; `is List<Int>` is an error, `is List<*>` is the only check.** Casts to a parameterised type are unchecked. [java-interop]
- **`wait()`/`notify()`, `getClass()`, `clone()`, `finalize()` have Kotlin equivalents or are unavailable on `Any`.** `foo::class.java`/`foo.javaClass`, `kotlin.Cloneable`, `java.util.concurrent` instead of monitors. [java-interop]
- **Kotlin inserts runtime null checks on public non-null parameters.** A Java caller passing `null` gets an NPE at the Kotlin boundary, which is the intended behaviour; do not add a redundant `?: throw` behind it, and do not "fix" it by widening to `T?`. [kotlin-from-java]
- **Lombok, Guava preconditions, `Optional` in Kotlin code.** `Optional<T>` return types from Kotlin are a Java-ism; use `T?`. Guava `checkNotNull`/`checkArgument` have stdlib twins. Android Lint `GuavaPreconditionsUsedInKotlin`. [android-lint] [exceptions]

### Serialization

- **kotlinx.serialization: every referenced type must be `@Serializable`; only backing-field properties are serialised; getter-only and delegated properties are skipped.** Grep for `@Serializable` classes whose properties reference non-annotated classes (compile error) or that compute values in getters expecting them in the output. [kxs-classes]
- **Defaults are not encoded by default; absent-with-default is "optional"; `null` for a non-nullable property is an error even with a default.** `encodeDefaults = false` is the `Json` default, so a wire consumer that needs the field sees it disappear when it equals the default. Use `@EncodeDefault` per property or `encodeDefaults = true` when the schema requires presence; `@Required` when input must contain it; `coerceInputValues = true` if `null`/unknown enums should fall back to defaults. [kxs-classes] [kxs-json]
- **`@Transient` needs a default and the key must not appear in input** (it is treated as unknown unless `ignoreUnknownKeys = true`). [kxs-classes]
- **Initialiser side effects and `init` validation.** Property initialisers are *not* called when the value is present in input; `init {}` blocks *do* run after decode, so `require(...)` in `init` is how to validate wire data, and a side-effecting initialiser is a bug. [kxs-classes]
- **Sealed polymorphism: give every subclass a `@SerialName`.** The default discriminator value is the fully qualified class name, which "can change if you refactor the class"; a rename or package move silently breaks every stored or in-flight document. `@SerialName` values must be unique within the hierarchy. `data object` variants serialise as `{"type":"Name"}`. [kxs-poly]
- **Static type decides what is written.** `Json.encodeToString(ownedProject)` with the variable typed as the subclass omits the discriminator; type the value as the base (`encodeToString<Project>(...)`) when the reader needs polymorphism. [kxs-poly]
- **Open/abstract/interface polymorphism needs a `SerializersModule` with every subclass registered; `Any`/open properties need `@Polymorphic`.** A missing registration is a runtime `SerializationException`, not a compile error. Prefer `sealed` so the compiler does the registration. [kxs-poly]
- **One `Json` instance, configured once, held in a top-level `val`.** Instances are immutable, thread-safe and cache per-class metadata; `Json { }` inside a hot function throws that away. [kxs-json]
- **`ignoreUnknownKeys` is a schema-evolution decision.** Default `false` means any new field from a newer producer fails decoding; for inbound data from other services it is almost always wanted (`true`), for strict config files it is not. `isLenient`, `allowTrailingComma`, `allowComments`, `allowSpecialFloatingPointValues` produce or accept non-RFC-8259 JSON; each needs a reason. `useAlternativeNames = false` is a real speed-up when `@JsonNames` is unused. [kxs-json]
- **`namingStrategy = SnakeCase` applies to `@SerialName` values too and defeats grep/rename.** Prefer per-property `@SerialName` unless the project has decided otherwise. [kxs-json]
- **Data class versioning on the wire.** Adding a property without a default makes old documents fail with `MissingFieldException`; removing a property makes new readers fail on old documents unless `ignoreUnknownKeys`; reordering is harmless for JSON but changes `componentN` and the generated constructor. Every wire-format data class change should be checked against stored data and other services' versions. [kxs-classes] [api-compat]
- **Jackson: `jackson-module-kotlin` must be registered (`jacksonObjectMapper()`/`registerKotlinModule()`), and it needs `kotlin-reflect`.** Without it Jackson cannot use the primary constructor. A JSON `null` into a non-null primitive (`Int`) becomes `0` silently unless `FAIL_ON_NULL_FOR_PRIMITIVES` is on; `KotlinFeature.StrictNullChecks` catches `null` elements in non-null collections at a performance cost. Sealed subclasses are auto-detected but the base still needs `@JsonTypeInfo`. Null for a non-null reified type throws `DatabindException` (2.19+), so code that relied on a silent `null` will now fail. [jackson-kotlin]
- **Do not mix `@Serializable` and Jackson annotations on the same class without a reason**, and do not put `java.io.Serializable` on Kotlin data classes casually (needs `serialVersionUID` in a companion; detekt `SerialVersionUIDInSerializableClass` active; Android Lint `SerializableUsage`). [detekt-style] [android-lint]

### API design and visibility

- **Everything is `public` by default; ask for `internal` or `private`.** Every new top-level `class`/`fun`/`val` and every member without a modifier is public API of the module. In an application module this is at worst clutter; in a library it is a compatibility promise. "Always explicitly specify member visibility." [visibility] [coding-conventions]
- **Libraries: explicit API mode on (`explicitApi()`), and explicit return types everywhere public.** Inferred return types "can change silently" and break binary compatibility (`JsonDeserializer` → `JsonOrXmlDeserializer` example). Explicit API mode makes both the modifier and the type mandatory for public declarations (exempt: primary constructors, data-class properties, accessors, overrides). [explicit-api] [api-compat] [coding-conventions]
- **Binary compatibility checked by tool, not by eye.** A library PR should carry the `api/*.api` diff (BCV `apiCheck`) or the KGP `abiValidation` dump; a changed dump is the review surface for compat. Widening (`List` → `Collection`) or narrowing (`Number` → `Int`) return types, adding parameters (even defaulted), adding abstract members, and changing annotation `@Target` all break something. [BCV] [api-compat] [whatsnew22]
- **No data classes, arrays, mutable collections or `Boolean` parameters in a public library API.** Covered above; the API guidelines say so explicitly. [api-compat] [api-predictability] [api-readability]
- **Deprecate before removing: `@Deprecated(message, replaceWith = ReplaceWith(...), level = WARNING → ERROR → HIDDEN)` across minor releases; removal only in a major.** A PR that deletes a public symbol without a deprecation cycle is blocking for a library. Delegating an old property to the new one (`var oldName by this::newName`) keeps it working during the cycle. [api-compat] [delegation]
- **`@RequiresOptIn` for experimental/delicate surfaces; propagate opt-ins; never use opt-in to deprecate.** A new public API marked experimental lets it change later; using an upstream experimental API without `@OptIn` is a compiler error or warning depending on the marker's level. [api-compat]
- **Public `inline` functions can only use public or `@PublishedApi` declarations, and their bodies are copied into callers.** A change to a public inline body is a behavioural change for consumers that have not recompiled. [inline] [api-compat]
- **Sealed hierarchies to prevent invalid extension; `final` by default is a feature.** Open a class only when subclassing is designed for; prefer composition/delegation. [api-predictability]
- **Core concept as members, everything else as extensions.** "Only regular properties, overrides, and overloaded operators should be declared as members by default"; computed properties and helpers are extensions, which also keeps the class small and the API composable. [api-readability]
- **DSL builders: required values as function parameters, options in the lambda; factory function named after the type (`Json { }`).** The compiler cannot check that a required property was set inside a lambda. [api-readability]
- **Numeric types: `Int`/`Long`/`Double` for arithmetic; a value class for an id; `Byte`/`Short`/`Float` only as memory-layout types; unsigned types only for full-range or native interop, not "because it is never negative".** [api-readability]
- **Meaningful `toString` on stateful public types, without sensitive data.** `toString` ends up in logs; never include passwords/tokens. [api-debuggability]
- **`@JvmName` to disambiguate erased overloads; `@file:JvmName` instead of `*Kt` facades.** [kotlin-from-java]
- **Context parameters (`context(...)`, preview in 2.2) and other `-X` features in a library's public API** lock consumers to a compiler flag. Flag any `freeCompilerArgs.add("-X…")` that affects public signatures. [whatsnew22] [gradle-compiler]

### Tests

- **Coroutine tests use `runTest`, not `runBlocking`, and inject the `TestDispatcher`.** `runTest` skips `delay`, times out at 60 s, and rethrows uncaught child exceptions; a hard-coded `Dispatchers.IO` inside the code under test makes its delays real and its coroutines invisible to `advanceUntilIdle()`. detekt `CoroutineLaunchedInTestWithoutRunTest` (inactive). [coroutines-test] [android-coroutines] [detekt-coroutines]
- **`StandardTestDispatcher` (queued; needs `runCurrent`/`advanceUntilIdle`) versus `UnconfinedTestDispatcher` (eager).** A test that passes only with `Unconfined` may be hiding an ordering assumption; a test that calls `advanceUntilIdle()` with no `Standard` dispatcher in play is doing nothing. Never-ending producers go in `backgroundScope`. `Dispatchers.setMain` must be paired with `resetMain` (`@AfterEach`). [coroutines-test]
- **Flows are asserted with Turbine (`flow.test { awaitItem(); awaitComplete() }`) or `toList()`/`first()` under `runTest`, not with `collect` + mutable list + `delay`.** Turbine fails on "Unconsumed events found", so `cancelAndIgnoreRemainingEvents()` at the end of a test is a yellow flag (what was ignored?). `testIn(backgroundScope)` for hot flows; emit after `test` has started or the value is dropped. Turbine's 3 s timeout is wall-clock, independent of virtual time. [turbine] [SharedFlow]
- **MockK: `relaxed = true` hides missing stubs.** A relaxed mock returns zero/empty/chained mocks for everything, so a test keeps passing when the code under test starts calling something new. Prefer strict mocks with explicit `every`, `relaxUnitFun = true` when only `Unit` functions are noise. `every { }` without any `verify { }` or assertion on the result tests nothing; `confirmVerified(mock)` and `checkUnnecessaryStub()` tighten. [mockk]
- **`mockkStatic`/`mockkObject`/`mockkConstructor` must be undone (`unmockkAll()` in `@AfterEach`, or the scoped block form)** or they leak into other tests in the same JVM. `spyk` on suspending functions has a known issue. [mockk]
- **Do not mock value types, collections, `File`, `System`.** MockK restricts these by default; mocking them "often signals poor architecture". Mocking a data class or a `List` means the design needs a seam, not a mock. [mockk]
- **`coEvery`/`coVerify` for suspend functions; `every` on a suspend function is a compile error or a wrong answer.** [mockk]
- **Kotest: the default `IsolationMode.SingleInstance` shares one spec instance across all tests**, so a `val list = mutableListOf()` in the spec body leaks between tests; use `InstancePerRoot` or reset in `beforeTest`. Pick one spec style per project (there are "no functional differences"). [kotest-isolation] [kotest-styles]
- **JUnit 5 in Kotlin** (general knowledge, the JUnit page was not fetched): `@BeforeAll`/`@AfterAll` need either a `companion object` with `@JvmStatic` or `@TestInstance(Lifecycle.PER_CLASS)`; `@Nested` classes must be `inner class`; `@MethodSource` factories likewise need `@JvmStatic` or `PER_CLASS`; `org.junit.jupiter.api.assertThrows<T> { }` is the reified Kotlin helper. Backtick test names (`` fun `adds two numbers`() ``) are allowed only in tests. [coding-conventions]
- **Time: no `Thread.sleep`, no `System.currentTimeMillis()`/`Clock.systemUTC()` in code under test.** Inject a `Clock`/`TimeSource`; under `runTest` use `testScheduler.timeSource` and `currentTime`; `withTimeout` inside `runTest` uses virtual time. detekt `SleepInsteadOfDelay` (active). [coroutines-test] [detekt-coroutines]
- **`lateinit var` in test fixtures is the one place it is idiomatic**; `@BeforeEach` initialises it. [properties]
- **Assertion libraries: one per project (kotlin.test, AssertJ, Kotest matchers, Strikt, Truth), not three.** `kotlin("test")` resolves to the JUnit variant the build selects (`useJUnitPlatform()` for JUnit 5); mixing `kotlin.test.assertEquals(expected, actual)` with AssertJ's `assertThat(actual).isEqualTo(expected)` flips argument order across files. [gradle-project]
- **A test for a `sealed`/exhaustive `when` or for a coroutine's cancellation should fail without the feature.** Ask of a new test: can it pass while the thing it checks is false (relaxed mocks, `cancelAndIgnoreRemainingEvents`, `advanceUntilIdle` with nothing scheduled, `runCatching` in the test body). [turbine] [mockk]
- **Android Lint test hygiene (general): `@Ignore` without a reason, assertions with side effects, expensive assertions.** `IgnoreWithoutReason`, `AssertionSideEffect`, `ExpensiveAssertion`. [android-lint]

### Build and dependencies

- **Kotlin Gradle plugin version is one literal, aligned across modules.** `kotlin("jvm") version "2.4.21"` "should be literal in this block"; many modules → settings `plugins {}` or the version catalog `[plugins]` with `alias(libs.plugins.kotlin.jvm)`. Mismatched KGP versions across modules, or a stdlib pinned to a different version than KGP, are the classic build smell; `kotlin-bom` aligns transitive stdlib artifacts. [gradle-project] [version-catalogs]
- **`compilerOptions {}`, not `kotlinOptions {}`.** `kotlinOptions` has been deprecated since 2.0 and is an *error* from 2.2.0; `android.kotlinOptions` migrates to `kotlin.compilerOptions`. `freeCompilerArgs` is slated for deprecation; prefer typed properties (`optIn.add`, `progressiveMode`, `jvmDefault`, `allWarningsAsErrors`). [gradle-compiler] [whatsnew22]
- **`jvmToolchain(N)` (or aligned `jvmTarget` + Java `targetCompatibility`).** The default `jvmTarget` is still `1.8`; mismatch fails the build (`jvmTargetValidationMode` default ERROR on Gradle 8+). A PR that sets `jvmTargetValidationMode = IGNORE`/`WARNING` is hiding the problem. [gradle-compiler] [gradle-project]
- **`allWarningsAsErrors = true` (and consider `extraWarnings = true`, `progressiveMode = true`).** With it, unused variables, deprecated API use, redundant modifiers and platform-type leaks are already blocking; without it the reviewer must look for them. A PR that turns it off, or adds `@Suppress` broadly, needs a reason. [gradle-compiler]
- **Libraries: `explicitApi()` and binary-compatibility validation in the build**, with the dump committed. BCV plugin is in maintenance mode; KGP's `abiValidation {}` is the successor but still experimental in 2.2 (`checkLegacyAbi`/`updateLegacyAbi`). Either is fine; neither is optional for a published library. [BCV] [whatsnew22] [explicit-api]
- **`api` only for types in public signatures; `implementation` for everything else.** "Prefer the implementation configuration over api when possible." A Kotlin library that returns a kotlinx.coroutines `Flow` or a `kotlinx.serialization` `Json` in its public API needs those as `api`; a logging framework never is. Leaking `implementation` types into public signatures fails consumers at compile time. `compileOnly` for annotations/processors; `runtimeOnly` for drivers. [gradle-api-impl]
- **Version catalog as the single place for versions; it does not pin.** `libs.versions.toml` centralises coordinates, but "Gradle may still select different versions due to dependency graph conflicts"; a `platform()`/BOM or `resolutionStrategy` is needed for true alignment. A PR adding a hard-coded `"group:artifact:1.2.3"` beside an existing catalog is inconsistent. [version-catalogs]
- **kotlinx library versions must be compatible with the Kotlin version.** `kotlinx-coroutines`, `kotlinx-serialization` (plugin `kotlin("plugin.serialization")` version must match KGP), `kotlinx-datetime`, and the test library are compiled against specific Kotlin releases; a Kotlin bump without bumping them, or the reverse, is the common breakage. `kotlinx-coroutines-test` belongs in `testImplementation` only. [coroutines-test] [gradle-project]
- **`kotlin("test")` picks JUnit 4 unless `useJUnitPlatform()` is set.** A JUnit 5 project that forgets `tasks.test { useJUnitPlatform() }` runs zero tests and reports green. [gradle-project]
- **`-X` flags in `freeCompilerArgs` are previews.** `-Xcontext-parameters`, `-Xname-based-destructuring`, `-Xnested-type-aliases`, `-Xexplicit-api` (prefer `explicitApi()`), `-Xjvm-default` (replaced by `jvmDefault`). Each one in a library build is a compatibility decision; `-Xcontext-receivers` and `-Xcontext-parameters` together are an error. [whatsnew22] [gradle-compiler]
- **`kotlin-reflect` on the classpath only when something uses it** (Jackson Kotlin module does). It is large and slows startup. [jackson-kotlin]
- **KMP: `kotlin("test")` in `commonTest`, platform dependencies in `<target>Main`, no JVM-only artifacts in `commonMain`.** [gradle-project] [kmp]
- **`buildSrc`/convention plugins over copy-pasted `build.gradle.kts` blocks**; a PR that adds the same `compilerOptions {}` to a fourth module should move it. [gradle-compiler]

## 4. Severity hints

**Blocking (correctness, data loss, leaks, security):**
- `GlobalScope` or unowned `CoroutineScope(...)` for request-scoped work; `launch(NonCancellable)`.
- `catch (e: Exception/Throwable)` or `runCatching` around suspending code without rethrowing `CancellationException`.
- `runBlocking` inside a `suspend` function or on a server thread pool.
- Blocking IO/JDBC/`Thread.sleep` in a `suspend` function without an IO dispatcher.
- `withContext`/`launch` inside `flow {}`; emitting from a catch that swallowed a downstream exception.
- `CoroutineExceptionHandler` on `async` or a child believed to handle errors (dead code hiding a crash path).
- `!!`, `map[k]!!`, `first()`, `as` on data that production can make null/empty/mismatched.
- `else` in a `when` over a sealed type or enum in domain logic (silent fall-through on a new variant).
- `associateBy`/`toMap` on keys that can collide when uniqueness matters; `zip` on lists that must match.
- Arrays or `var` properties in data classes used as keys or compared; `===` on strings/value classes.
- Mutable collection/`MutableStateFlow` exposed publicly; downcast `List` → `MutableList`.
- `@Serializable` sealed subclasses without `@SerialName`; wire data class changes without defaults; `null` into non-null primitives via Jackson without `FAIL_ON_NULL_FOR_PRIMITIVES`.
- Swallowed exceptions (`catch` that logs a string only, `onFailure { }` that logs only).
- `TODO()` in production paths.
- Library: public symbol removed/narrowed/widened without deprecation; data class or `Boolean` parameter added to a public API; `.api` dump changed without acknowledgement; `kotlinOptions` (fails on 2.2 anyway).
- Tests: `relaxed = true` + no verification; `cancelAndIgnoreRemainingEvents()` hiding emissions; mocks never `unmockk`ed; `useJUnitPlatform()` missing.

**Should fix (design and maintainability, likely bugs later):**
- Hard-coded `Dispatchers.*`; `Dispatchers.Unconfined` anywhere in production.
- `async` never awaited; async-style `fooAsync(): Deferred` functions; `suspend fun` returning `Flow`.
- Missing `ensureActive()`/`yield()` in long loops; suspending cleanup in `finally` without `NonCancellable`.
- `StateFlow` used for events, `SharedFlow` for state, `value = value + 1` instead of `update {}`.
- `lateinit` outside DI/test setup; `?.let { } ?: run { }` control flow; `Any?` parameters.
- Platform types inferred into `internal`/`public` declarations.
- Public-by-default declarations in a module that should expose a few; missing `internal`.
- `Pair`/`Triple` in signatures; positional destructuring of 3+ fields; `object` exceptions.
- `Result<T>` as a domain return type; mixed throw-vs-null conventions in one API.
- Nested scope functions; `inline` with no lambda; `infix` on mutators; `operator` abuse.
- Long eager chains over large collections without `asSequence()`; `Array<Int>`; spread in hot paths.
- `Json { }` built per call; `ignoreUnknownKeys` unset on inbound data; `namingStrategy` globally.
- `api` where `implementation` suffices; hard-coded versions beside a catalog; kotlinx versions not matching Kotlin; `jvmTargetValidationMode` relaxed; `allWarningsAsErrors` turned off.
- Kotest `SingleInstance` with mutable spec state; several assertion libraries; `Thread.sleep` in tests.

**Nit (style the tooling may not cover):**
- `if` vs `when` choice; expression bodies; `..<`; `for` vs `forEach`; `it` vs named parameter in nested lambdas; `"$name"` vs `"${name}"`; `const val`; `data object` vs `object`; `entries` vs `values()`; `MayBeConstant`; redundant `Unit` return type; `@JvmStatic`/`@JvmOverloads` on code with no Java callers; `typealias` naming.

## 6. Open questions / disagreements

- **`!!` tolerance.** The null-safety page only says use it when "you are confident"; Android Lint and most style guides forbid it in production. Teams differ on whether `!!` with a justifying comment is acceptable. Default here: flag, accept with a comment that states the invariant and why `requireNotNull` with a message is not better.
- **`else` in `when` over sealed types.** The API guidelines and detekt (`ElseCaseInsteadOfExhaustiveWhen`) say omit it; some teams add `else -> error("unreachable")` for defensive logging in generated or reflective code. The compiler already rejects non-exhaustive `when` (statement or expression) since 1.7, so the defensive `else` only hides new variants. Recommend flagging; allow in `commonMain` for `expect` sealed classes where the docs say `else` is required.
- **Catching `CancellationException` explicitly versus `currentCoroutineContext().ensureActive()` in the catch.** Both patterns appear in official material (the cancellation page rethrows; the NonCancellable page uses `ensureActive()`). Either is acceptable; a bare `catch (e: Exception)` with neither is the defect.
- **`Result<T>` as a return type.** The KEEP says not for domain errors; a sizeable part of the community (Arrow `Either`, kotlin-result) disagrees and uses typed results widely. Treat stdlib `Result` in signatures as "should fix", and third-party typed results as a project convention to respect.
- **`relaxed = true` in MockK.** The MockK page does not call it out as harmful; it documents it neutrally and warns only about generic return types. The "hides missing stubs" concern is practitioner consensus, not vendor guidance. Keep it at should-fix.
- **Sort stability.** The ordering page makes no stability promise; Kotlin/JVM delegates to `java.util.Arrays.sort`/`List.sort` (stable, TimSort) and most code relies on it. In `commonMain` or Native/JS targets treat stability as unverified from these sources.
- **ktlint rule inventory and JUnit Kotlin guidance** were not fetched (404s). The items marked "unverified" rest on general knowledge; confirm against https://pinterest.github.io/ktlint and the JUnit user guide when those pages are reachable.
- **`Dispatchers.IO` versus `limitedParallelism`.** The IO docs recommend views per blocking resource (DB pool size, etc.); many codebases use a single `Dispatchers.IO` for everything. Not a defect, but a scaling question worth raising when a PR introduces a new blocking resource.
- **Data classes in *application* (not library) APIs.** The API guidelines target published libraries; inside an application or between modules of one repo, data classes for DTOs are idiomatic (the Idioms page's first example). Apply the "no data class in public API" rule to artifacts consumed outside the repo.
- **Name-based destructuring** is stable only in `only-syntax` mode as of 2.5.0-Beta2; `complete` mode changes the meaning of `val (a, b) = x`. Review build flag changes in this area as behaviour changes, not style.
- **`kotlinOptions` → `compilerOptions`.** Error since 2.2.0; projects still on 2.0/2.1 see a deprecation warning only. Severity depends on the project's Kotlin version.
