# Contract: sidecar protocol changes (1.1 → 1.2)

All additions are optional fields, new messages, one new rpc and new fixtures — a minor bump under
`protocol/README.md`'s rule. A 1.2 sidecar accepts a 1.1 SDK.

## `discovery.proto`

```proto
enum Kind {
  // … existing 0–6 …
  AUTONOMOUS_AGENT = 7;
}

message Component {
  // … existing …
  oneof detail {
    // … existing 10–16 …
    AutonomousAgentDetail autonomous_agent = 17;
  }
}

// An autonomous agent's whole definition. There is no per-task plan: the sidecar runs the loop
// from this and asks the process only to run a tool, check a guardrail and check a task rule.
message AutonomousAgentDetail {
  string description = 1;                   // required
  optional string instructions = 2;
  repeated Tool tools = 3;                  // as AgentDetail.tools
  repeated string guardrails = 4;
  repeated TaskType task_types = 5;         // every type this agent accepts, declared once
  repeated TaskAcceptance accepts = 6;
  optional AutonomousSettings settings = 7;
  optional string model = 8;                // a name in the sidecar's configuration; absent: default

  message TaskType {
    string name = 1;                        // the wire name
    string description = 2;
    optional string result_schema_json = 3; // absent: the result is text
    repeated string rules = 4;              // names, checked through Agent.CheckTaskRule in order
  }
  message TaskAcceptance {
    string task_type = 1;                   // a name in task_types
    int32 max_iterations = 2;               // ≥ 1
  }
  message AutonomousSettings {
    optional double approaching_budget_at = 1;    // 0.8
    optional int32 repeated_failure_at = 2;       // 3
    optional int32 max_consecutive_failures = 3;  // 5
    optional int64 dependency_stuck_after_millis = 4;   // 300000
  }
}
```

`Discovery.validate` refuses: an empty description; no `accepts`; an acceptance naming a type not
in `task_types`; a type accepted twice; `max_iterations < 1`; a `result_schema_json` that is not
JSON; a tool, guardrail, task type or rule name empty or duplicated; a tool named `complete_task` or
`fail_task`.

## `agent.proto`

```proto
service Agent {
  // … Plan, InvokeTool, CheckGuardrail …
  rpc CheckTaskResult (TaskResultRequest) returns (TaskResultVerdict);
}

message TaskResultRequest {
  string component_id = 1;
  string task_id = 2;
  string task_type = 3;
  string result_json = 4;                   // as the model passed it to complete_task
}

message TaskResultVerdict {
  oneof verdict {
    Empty accept = 1;
    string malformed = 2;                   // does not decode as the type's result: a tool error for the model
    Rejection reject = 3;                   // the first rule, in declaration order, that refused it
  }
  message Rejection { string rule = 1; string reason = 2; }
}
```

One call per completion, not one per rule: only the process knows the result's type, so it decodes the
result and runs every rule in order. Without it a remote task type with no rules would accept a result
that does not match its shape. A rule that throws is a gRPC error, which the sidecar treats as a failed
iteration and tries again.

`InvokeTool` and `CheckGuardrail` are reused with `session_id = "task:<task id>"`. A `ToolRequest`
for a built-in never reaches the process.

## `client.proto`

No new rpc. The sidecar's `Client.Invoke` and `Client.InvokeStream` accept `kind = AUTONOMOUS_AGENT`:

| `name` | payload (JSON, manifest) | reply |
|---|---|---|
| `assign` | `{"taskIds":[…]}` `agent-assign` | `Done` |
| `run-single-task` | `{"taskId": "…"}` `agent-run-single` | `{"instanceId": "…"}` `agent-instance-ref`; `entity_id` ignored |
| `suspend`, `resume`, `terminate` | empty | `Done` |
| `state` | empty | `AgentState` `agent-state` |
| `notifications` (InvokeStream) | empty | tokens: one JSON `Notification` each |

Task operations are `Client.Invoke` with `kind = EVENT_SOURCED_ENTITY`, `component_id =
"ankka-task"`, and the entity's own handler names (`create`, `add-dependent`, `assign`, `unassign`,
`start`, `reject-result`, `complete`, `fail`, `cancel`, `get`), payloads under the manifests
`data-model.md` §2 implies (`task-create`, `task-assign`, …). `TaskCalls.create`'s ordering
(create, index dependents, check terminal) is implemented in each SDK's client, and `await` is a
client-side poll of `get`. The sidecar's `ClientService` retries `Unavailable` as it does today.

## Fixtures (`protocol/fixtures/autonomous/`)

`task-created.json`, `task-completed.json`, `agent-instance-iteration-completed.json`,
`agent-notification-task-result-rejected.json`, `agent-state.json` — regenerated by
`AutonomousFixturesSuite` in `modules/testkit` (a directory of their own: `core`'s `EncodingFixturesSuite` owns the top-level files), checked by `test_encoding_fixtures.py` and the TypeScript equivalent.

## Versions

`Discovery.ProtocolVersion` → `"1.2"`; `controlplane-api` `Protocol.version` → `"1.2"`; Python
`PROTOCOL_VERSION` and TypeScript `PROTOCOL_VERSION` → `"1.2"`; `protocol/README.md`,
`docs/reference/sidecar-protocol.md` and `docs/concepts/polyglot.md` say 1.2 (they say 1.0 today
and the code says 1.1; both go).
