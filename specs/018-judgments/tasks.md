# Tasks: Judgments — Fast, Typed Decisions from a System One Model

**Input**: Design documents from `/specs/018-judgments/`

**Prerequisites**: [plan.md](./plan.md), [spec.md](./spec.md), [research.md](./research.md),
[data-model.md](./data-model.md), [contracts/](./contracts/), [quickstart.md](./quickstart.md)

**Tests**: included. Every acceptance scenario in the spec is an automated test that runs offline
with no key (SC-005), and this repository's rule is that a guarantee nobody measured is a comment.
Where a task says "case", it means a `test(...)` in the named suite.

## Format: `[ID] [P?] [Story] Description`

- **[P]**: can run in parallel — different files, no dependency on an incomplete task
- **[Story]**: US1 (a handler asks typed questions and reads typed answers), US2 (a service is
  pointed at Jev), US3 (a guardrail that asks), US4 (it is tested with a script), US5 (what a
  judgment cost, and who answered), US6 (it is documented)

Paths are repository-relative. Abbreviations: `AG` =
`modules/agent/src/main/scala/com/thinkmorestupidless/ankka/agent`, `AGT` =
`modules/agent/src/test/scala/com/thinkmorestupidless/ankka/agent`; `JG` = `AG/judgment`, `JGT` =
`AGT/judgment` (offline suites that need nothing but `agent`), `JGR` =
`modules/agent/src/test/resources/judgment`; `AUTO` = `AG/autonomous`; `TKT` =
`modules/testkit/src/test/scala/com/thinkmorestupidless/ankka/testkit` (every suite that needs
`EventSourcedTestKit` or `AnkkaTestKit`, since `testkit` depends on `agent`), `TKA` =
`TKT/autonomous`, `TKR` = `modules/testkit/src/test/resources/journal`; `DOCS` = `docs`; `SKILL` =
`tools/docs/skill`. "R*n*" is a section of `research.md`; "§*n*" a section of `data-model.md` or
of the named contract.

## Implementation strategy

**MVP is Phase 1 + Phase 2 + US1** (T001–T010): a handler asks a scripted provider typed
questions and its caller reads typed answers. **US2** makes it real, and is the other half of the
P1 set — ship nothing before both. **US3** is the use the seam is most obviously for and is the
largest phase, because it is the only one that changes how existing code runs: T014 lands alone,
behaviour-preserving, with every existing suite green, before a judged guardrail exists. **US4**
pins the tool the other stories already lean on. **US5** is the only phase that changes what is
stored, which is why T001 comes first of all. **US6** is what makes any of it true for the reader
who arrives with one page.

Ship in one pull request as one release: nothing here has an intermediate state worth a release
of its own, and the additions to `AgentRuntime`, the effect and session memory move together.
Land the phases as commits in this order so the branch is demonstrable at each checkpoint.

T013 and T036 need a TypeSafe key, which only the user can supply. Everything else runs offline.
Without a key the feature is complete and tested against the provider's documentation, and the
first run with one is the step that confirms or corrects `contracts/provider-wire.md`.
