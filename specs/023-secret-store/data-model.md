# Data Model: Secret Store

What is stored, where, and by whom. Decisions are in [research.md](research.md).

## Service secret (a row of the service's own database)

Table `ankka_secrets`, created by `kustomization/components/postgres/ddl/40-secrets-postgres.sql`.

| Column | Type | Notes |
|---|---|---|
| `name` | `TEXT PRIMARY KEY` | letters, digits, `.`, `_`, `-`, `/`; 1 to 253 characters |
| `ciphertext` | `BYTEA NOT NULL` | the stored form, below |
| `updated_at` | `TIMESTAMPTZ NOT NULL DEFAULT now()` | set on every `put` |

- One row per name. `put` is an upsert; `delete` removes the row.
- The table is read and written by the secret store alone. No journal, snapshot, durable state,
  timer, projection or view row table holds a service secret, and no projection reads this table.
- Two services never share a database, so there is no service column.

**Stored form** of `ciphertext`:

| Bytes | Content |
|---|---|
| 1 | the form's version, `0x01` |
| 12 | the nonce, random per `put` |
| n + 16 | AES-256-GCM of the value's UTF-8 bytes, with the tag; the associated data is the name's UTF-8 bytes |

A value is 1 to 65,536 bytes, so a row's `ciphertext` is 30 to 65,565 bytes.

**Lifecycle**: absent → kept (`put`) → replaced (`put` again; one row) → absent (`delete`). There
is no history and no version of a value.

## Secret key (a service's, one value)

| Where | Form |
|---|---|
| configuration | `ankka.secrets.key`, from `ANKKA_SECRET_KEY`: standard base64 of 32 bytes |
| deployed | a Secret `<service>-secret-key` in the project's namespace, entry `key`, made once by the operator and kept when the service is deleted |
| a developer's machine | the developer's environment |
| a test | generated by the test kit, per kit |

States: not set (the service runs; keeping and reading fail naming the variable), set (the store
works), set and malformed (the service does not start). The key is never written to the database,
the journal, a log or a message of the protocol.

## Project secret (a Kubernetes Secret, and the control plane's record of it)

**In the cluster**: a Secret in the project's namespace, type `Opaque`, named by the member within
the rules of [contracts/control-plane.md](contracts/control-plane.md), holding the entries.
Written by the control plane, read by the kubelet when a pod starts, read back by nobody.

**In the control plane**: part of the `Project` entity's state.

```scala
final case class ProjectSecretRef(
    entries: Set[String],
    setBy: Option[Actor] = None,
    setAt: Option[Instant] = None)

final case class Project(…, secrets: Map[String, ProjectSecretRef] = Map.empty)
```

| Event | Fold |
|---|---|
| `ProjectSecretEntriesSet(name, entries, actor, at)` | the secret's entries become its entries ∪ `entries`; `setBy` and `setAt` are the event's |
| `ProjectSecretEntryRemoved(name, entry, actor, at)` | `entry` leaves the secret's entries; a secret left with none leaves the map, and returns to it when an entry is next set |

- No event and no state holds a value.
- A tombstoned project keeps its record; its Secrets stay in a namespace nothing deploys to.
- The record and the cluster can differ in one direction only: an entry written to the cluster
  whose record failed to persist. Setting it again repairs it. The reverse cannot happen, because
  the cluster is written first.

## Platform variables (a declaration, not data)

`PlatformVariables` in `core`; its parts and readers are in
[contracts/operator.md](contracts/operator.md). It is the only place a variable's standing is
written.

## What does not change

- No field is added to `AnkkaServiceSpec` or to `ankkaservice.yaml`.
- No existing table, event or stored form changes. `Project` gains a field with a default.
- No grant changes, for the operator or the control plane.
