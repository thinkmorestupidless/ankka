# Contract: the wire at protocol 1.15

Additive by `protocol/README.md`'s rule, so a minor. Gated on both sides as socket routes (1.9) are,
because a 1.14 SDK that declared a workflow source against a 1.15 runtime would otherwise be handed
changes with no standing and no error.

## `payload.proto`

```proto
// 1.15: where a workflow stands once the effect that recorded a state is applied. Carried on a
// view's or a consumer's request for a change from a workflow source, and on nothing else.
message WorkflowStanding {
  string status = 1;                 // NotStarted, Running, Paused, Completed, Failed, or Unknown for a state recorded before 1.15
  optional string step = 2;          // the step the workflow is on or waits after
  map<string, int32> retries = 3;    // retries so far, per step
  optional string failure = 4;       // why it failed, when it did
}
```

## `view.proto`

```proto
message ViewRequest {
  string component_id = 1;
  Payload event = 2;                 // for a workflow source: the state the workflow recorded
  Metadata metadata = 3;             // ce-subject: the workflow's id; ankka.sequence: the record's
  optional Payload row = 4;
  bool deleted = 5;
  optional string source_id = 6;
  optional WorkflowStanding standing = 7;   // 1.15: present for a workflow source only
}
```

## `consumer.proto`

```proto
message ConsumerRequest {
  string component_id = 1;
  Payload message = 2;
  Metadata metadata = 3;
  bool deleted = 4;
  optional WorkflowStanding standing = 5;   // 1.15: present for a workflow source only
}
```

## `discovery.proto`

No field changes. `Source.ComponentRef` with `kind = WORKFLOW` is now accepted for a `ViewDetail`'s
`source`, any of a keyed view's `sources`, and a `ConsumerDetail`'s `source`. A start position, a
contract, a broker or `parallel` on it is refused as on an entity source.

## What discovery refuses (sidecar, `Discovery.validate`)

| Spec | Refusal |
|---|---|
| a workflow source from a Spec whose minor is below 15 | `view 'x' reads workflow 'w', which needs protocol 1.15; the SDK speaks 1.14` |
| a workflow source naming a component the Spec does not declare | as today: `view 'x' subscribes to Workflow 'w', which is not declared` |
| a start position, contract, broker or parallel on a workflow source | as today for an entity source |
| a keyed view reading a topic and a workflow | `a topic and a workflow may not be sources of one view` |

## What an SDK refuses (each SDK's discovery)

A runtime stating a protocol below 1.15 when any view, keyed view or consumer declares a workflow
source: the SDK answers discovery with `FAILED_PRECONDITION` naming the classes and both versions,
in the form of its 1.13 and 1.14 refusals:

```
CheckoutRows, CheckoutEnds read a workflow, which the sidecar does not know: it speaks protocol
1.14, and this SDK 1.15. Run a sidecar speaking 1.15 or later.
```

## The change a process is handed

For each `state` record the workflow journalled, in the order recorded, exactly once to a view and
at least once to a consumer:

- `event` / `message`: the state, as a `Payload` whose manifest is the workflow's state manifest
  (for a process's own workflow, the manifest the process gave when it recorded the state);
- `metadata`: `ce-subject` the workflow's id, `ankka.sequence` the record's sequence number, and on
  a consumer's request `ankka.protocol` `1.15`;
- `standing`: as above.

For a `delete` record: `deleted = true`, no `event`, no `standing`. For any other record kind:
nothing is sent.

## Compatibility

| SDK | Runtime | Outcome |
|---|---|---|
| 1.14 | 1.15 | runs; a workflow source is refused at discovery naming the versions |
| 1.15 | 1.14 | runs; the SDK refuses discovery when it declares a workflow source |
| 1.15 | 1.15 | workflow sources |

`protocol/README.md` states `1.15`; `WireProtocol.Version`, each SDK's `PROTOCOL_VERSION` and
`controlplane-api`'s `Compatibility` say the same. The three SDK copies of `protocol/` are
regenerated by their copy scripts and CI holds them identical.
