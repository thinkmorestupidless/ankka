# Research: Go SDK

**Feature**: [spec.md](./spec.md) | **Plan**: [plan.md](./plan.md)

Each finding says whether it was verified against this repository, against upstream sources
fetched on 2026-10-23, or is an assumption a named task settles at implementation. The list at the
end collects the latter. The TypeScript SDK's research (`specs/013-typescript-sdk/research.md`)
made most of the shape decisions for a process SDK; this document checks which of them hold for Go
and decides the ones that are Go's own.

## R1 — Go 1.26 is the floor, 1.27 is current, both in the matrix

**Verified upstream** (go.dev/doc/devel/release). Go 1.27.0 was released 2026-08-19 (1.27.3 on
2026-10-19); Go 1.26.0 on 2026-02-10 (1.26.10 on 2026-10-19); Go 1.25.0 on 2025-08-12 and its last
minor, 1.25.14, on the day 1.27 shipped. The policy: "Each major Go release is supported until there
are two newer major releases", so today 1.26 and 1.27 are supported and 1.25 is not. Go 1.27 adds
generic methods, `encoding/json/v2` (on by default, opt-out `GOEXPERIMENT=nojsonv2`, not called
stable) and `go doc pkg@version`; nothing in it changes module versions or `debug.ReadBuildInfo`.
grpc-go 1.81.0 (2026-05-04) raised its minimum to Go 1.25 and 1.84.0 (2026-09-17) is current.

**Decision**: `go 1.26` in the SDK's `go.mod`, which is the floor the toolchain itself enforces: an
older `go` command refuses to build the module and names the version (FR-034), and a newer one needs
nothing. The getting-started page and the image build use 1.27. The SDK's CI job runs on both 1.26
and 1.27, as the TypeScript job runs on both Node lines, so the floor is a fact and not a claim. The
SDK uses nothing newer than 1.26: range-over-function iterators (`iter.Seq`, 1.23) for streams,
`testing.TB`, generics; no generic methods, no `encoding/json/v2`.

**Alternatives considered**: a 1.27 floor for `json/v2` (rejected: the codec is the SDK's own in
any case, R3, and a two-month-old floor excludes the half of the audience that upgrades once a year);
a 1.25 floor (rejected: unsupported since August, and grpc-go has already left it).

## R2 — Transport: grpc-go, stubs generated by Go tools and committed

**Verified upstream** (grpc-go releases; the protobuf-go and buf module pages) and **in this
repository** (`protocol/src/main/protobuf/ankka/protocol/v1/*.proto`; `sdks/typescript/scripts/proto.ts`;
`sdks/rust/scripts/proto.sh`; the Rust crate commits its generated code into the crate because a
published artifact must build alone). The protocol is eleven services: `Discovery`, `Client`
(fourteen unary rpcs and four server-streaming ones, `InvokeStream`, `QueryStream`, `Watch`,
`AwaitEndStream`), `EventSourced`, `KeyValue` and `Workflow` (one bidi `Handle` each), `Http`
(`Handle` unary, `HandleStream` server-streaming, `HandleSocket` bidi), `Mcp`, `Consumer`, `View`,
`TimedAction` and `Agent` (unary). grpc-go is the reference implementation the sidecar's grpc-java
is tested against upstream; its generated server interface for a bidi method is
`Handle(grpc.BidiStreamingServer[In, Out]) error`, one goroutine per stream, `Recv` in a loop and
`Send` from any goroutine as long as sends do not overlap.

**Decision**: `google.golang.org/grpc` v1.84 and `google.golang.org/protobuf` v1.36 as the SDK's
two runtime dependencies. Stubs are generated by `buf generate` with `protoc-gen-go` and
`protoc-gen-go-grpc` into `internal/pb/`, **and committed**: the mirror repository the release
produces (R8) is `sdks/go` as it stands, and `go get` runs no generator, so a Go module ships its
generated code. The three generators are Go programs, pinned as `tool` directives in a nested
module, `sdks/go/tools/go.mod`, so `go tool buf generate` needs nothing installed and the tools'
dependency graph never reaches a consumer (a nested module is not part of its parent). The protocol
copy lives at `sdks/go/protocol/` (protos, fixtures, `ENCODING.md`, `README.md`), copied by
`scripts/proto.sh`, which then regenerates; CI diffs the copy against `protocol/` **and** regenerates
into a temporary directory and diffs `internal/pb/`, so a protocol change that was copied but not
regenerated fails the build (FR-029). The first task is a spike of the event sourced conversation
against the sidecar image, as the TypeScript plan's was, because the evidence for grpc-go against
grpc-java is upstream's and not this protocol's: init, replay, snapshot request, a clean close on
passivation, an abort on a sidecar kill.

**Alternatives considered**: Connect-Go (rejected: nothing to gain over grpc-go for a server that
speaks only gRPC to one peer, and a third dependency); generating at `go generate` time by the
developer (rejected: a module on the proxy must build with `go build` alone); keeping the tools in
the main module's `go.mod` (rejected: Go 1.24 tool directives are ordinary requirements, and buf's
dependency graph would appear in every consumer's module graph).

## R3 — The codec reads struct types and tags by reflection; the encoding's rules are the SDK's, not `encoding/json`'s

**Verified in this repository**: `protocol/ENCODING.md` and the 38 fixtures (23 top-level, plus
`autonomous/`, `graph-deltas/`, `contracts/`, `secrets/`, `storage/`, `topics/`). Every field written
including `null` and `[]`; a `Long` past 2⁵³ round-trips; doubles render as jsoniter does (`1.0`,
`1.0E10`); an `Instant` keeps 0, 3, 6 or 9 fractional digits; a fieldless enumeration as a field is
`{"type":"Ready"}`; a sum type is the case's fields plus `"type"`; the fixtures compare bytes, so
field *order* is the declared order; reading is lenient where writing is strict (an absent optional
reads as none, an unknown field is ignored). **Verified upstream** (Go's `reflect` and
`encoding/json` documentation; the 1.27 notes): `encoding/json` decodes any JSON number into a
`float64` when the target is `any`, applies a zero value to a missing field, honours `omitempty`,
writes map keys sorted, and (v2) is still a different set of rules; none of them can be told to
write `1.0` for a whole double, inject a `type` discriminator from a registered case, or refuse a
missing required field. `reflect` gives field order, tags, embedded fields and unexported fields
(`PkgPath != ""`).

**Decision** (clarified in the spec): the codec walks the developer's struct types with `reflect`
**once, at registration**, building a per-type plan (field order, names, kinds, nested plans) that
encoding and decoding then follow without further reflection on the hot path. Names come from the
`json` tag's name, because that is what Go developers already write and what every tool reads, with
the Go field name lower-camel-cased when there is no tag; any `json` tag *option* (`omitempty`,
`string`, `omitzero`) is **refused at registration**, since each would change the bytes, and `-`
excludes the field. The Go type decides the encoding: `int`, `int32` → integer; `int64` → long;
`int16` → short; `int8` → byte; `float64` → double; `float32` → float; `bool`; `string`;
`time.Time` → instant; `time.Duration` → duration; `[]byte` → bytes; `[]T` → sequence (`nil` writes
`[]`); `map[string]T` → object; a struct → record; a pointer → optional (`nil` ↔ `null`); an
interface → a sum type whose cases are **registered** (`ankka.Cases[I]`, each case a struct type
under its discriminator); a named string type with registered values → an enumeration. Unsigned
integers, non-string map keys, channels, functions, unexported fields, an interface with no
registered cases, `any`, and an `omitempty` are refused at registration and in the component test
kit, naming the field (FR-013). Writing: the SDK's own JSON writer in declared field order; doubles
through a Scala-`Double.toString` renderer (shortest round-trip digits, decimal between 10⁻³ and
10⁷, otherwise `d.dddE±n`); instants in UTC with the digits they carry. Reading: the SDK's own
tokenizer over `encoding/json`'s `Decoder` with `UseNumber`, so an integer is never a `float64` on
the way; a missing non-pointer field, an unknown `type`, a fraction where an integer is declared,
refuse with the path. `time.Time` is normalised to UTC with its monotonic reading stripped before it
is written, so two reads compare equal (an edge case in the spec).

**Alternatives considered**: `encoding/json` v1 or v2 with custom marshalers (rejected: every type
would need one, and the rules above are not expressible as options); a schema DSL like the TypeScript
SDK's (rejected at clarify: Go has the types TypeScript erases, so declaring them twice is the cost
with no gain); code generation (rejected at clarify: a build step the spec rules out); an `ankka:`
tag of the SDK's own for names (rejected: a second spelling for what `json:"name"` already says; the
SDK's own tag is kept for what `json` cannot say, R5's `desc` for tool inputs).

## R4 — Time values: the standard library's where it has one, two small types where it does not

**Verified upstream**: `time.Time` holds nanoseconds and a monotonic reading; `time.Duration` is an
`int64` of nanoseconds; Go has no date-only or local date-time type. **Verified in this
repository**: the fixtures carry instants to 6 digits and the encoding allows 9; a `Duration` is
ISO-8601 (`PT1.5S`); `FiniteDuration` at the top level is `duration-millis` text; `LocalDate` and
`LocalDateTime` are ISO strings.

**Decision**: `time.Time` is the instant and `time.Duration` the duration, rendered by the codec as
the encoding says (a `time.Duration` cannot hold a day or more than about 292 years; ISO durations
with date parts are refused on read, naming the value). `ankka.LocalDate` and `ankka.LocalDateTime`
are string-backed value types with `Parse` and `String` and a `time.Time` conversion.

## R5 — What the compiler refuses, what registration refuses

**Verified in this repository**: the Scala `query` accepts only a `ReadOnlyEffect`; the TypeScript
SDK makes it a compile error through the handler's return type and re-checks at registration; the
sidecar accepts no events from a read-only handler. **Verified upstream**: Go's type system has
distinct named types and generics but no sum types, no required struct fields and no way to refuse
`nil` for an interface parameter at compile time.

**Decision**: three guarantees, each as strong as Go allows and backed at registration. (1)
`ankka.Query` takes a function returning `ReadOnlyEffect[S, R]`, a type no persisting builder
produces, so a query that persists does not compile; registration checks the kind again for a
caller who built the effect another way; the sidecar refuses regardless. (2) An endpoint is made by
`ankka.NewEndpoint(prefix, acl, routes...)`, so a program that states no ACL does not compile; a
`nil` ACL compiles and is refused at registration naming the endpoint (SC-005 counts this as the
compiler's refusal; the spec's edge case says both). (3) Handlers, steps, actions, tools, routes and
the client are generic over their input and reply types, so a handler declared with the wrong
input type for a declared codec is a compile error and no reflection touches the developer's
functions; only the value types are reflected (R3). A tool's input struct carries a `desc:"..."`
tag per field for the JSON Schema the model is given, derived from the same plan the codec uses
(FR-014). Every declaration problem is a value appended to the service's list, and `Service.Start`
refuses once naming them all (FR-005).

## R6 — The server: one goroutine per conversation, one sender, two slots for a workflow, panics recovered

**Verified in this repository**: `sidecar/.claude` rules and `sdks/typescript/src/server/*.ts`:
one command in flight per stateful stream, replies in order with the sidecar's id, a reply computed
from the state after its events, a snapshot included exactly when asked, a workflow answering commands
mid-step from the pre-step state and refusing a second concurrent step, stream end releasing state and
indistinguishable from passivation, a thrown handler a `Failure` and never a silent no-reply.
**Verified upstream**: grpc-go allows `Send` from any goroutine but not two at once; a server stream's
`Context()` is cancelled when the peer goes away; `GracefulStop` waits for streams to end and
`Stop` does not.

**Decision**: each `Handle` stream is the goroutine grpc-go gives it, its locals the instance's
state, commands awaited in order inside it, which makes one-in-flight true without a lock. The
workflow handler starts a step in a second goroutine on a fresh instance and both reply through one
channel drained by the stream's goroutine, so sends never overlap and a query mid-step is answered
from the pre-step state; a second step while one runs is refused. Every handler call is wrapped by
`recover()`, turning a panic into that request's `Failure` with the state unchanged (FR-021); a
`nil, err` return is the same failure; a refusal is an effect. Handlers receive a `context.Context`
derived from the stream's, cancelled when the conversation ends, so a wait inside a handler stops
when its request does (FR-007); the request's HTTP details and the caller are values on that context
(`ankka.RequestFrom(ctx)`), the Go equivalent of the Python `ContextVar` and Node `AsyncLocalStorage`.
On `SIGTERM` or `SIGINT` the server calls `GracefulStop` with a deadline and then `Stop`, so handlers
in flight finish within the time the platform gives and the process exits (FR-023). The SDK starts no
goroutine it does not own; a goroutine the developer starts is theirs, and the reference page says so
(the spec's edge case).

## R7 — Test kits under `go test`: testcontainers-go, the DDL copied out of the image through the Docker client

**Verified upstream** (pkg.go.dev): `github.com/testcontainers/testcontainers-go` v0.44.0
(2026-08-07) with `modules/postgres` (`postgres.Run(ctx, image, opts...)`, `WithInitScripts`,
`WithDatabase/Username/Password`), `GenericContainer` with `ExposedPorts`, `Env`, `HostConfigModifier`
for `ExtraHosts`, `WaitingFor` with `wait.ForHTTP(...).WithPort(...)` and `wait.ForAll`, `Network`,
and a Docker client (`testcontainers.NewDockerClientWithOpts`) whose `ContainerCreate` and
`CopyFromContainer` read a path out of an image without running it. **Verified in this repository**:
the TypeScript kit takes `/opt/docker/ddl` out of the sidecar image with `docker create` and `docker
cp`, chmods it 0755/0644, mounts it as the init scripts, sets `host.docker.internal:host-gateway`,
waits on `/_ankka/health` and `forListeningPorts`, gives the sidecar `ANKKA_PROCESS_ADDRESS`,
`ANKKA_SIDECAR_BIND=0.0.0.0`, `ANKKA_HTTP_PORT`, `ANKKA_DB_*`, a random `ANKKA_SECRET_KEY` and the
test's own variables, restarts the sidecar against the same Postgres, and `startBeside` runs another
image on the same network and journal; the process binds `0.0.0.0:0` for the kit and loopback
otherwise; the image is `$ANKKA_SIDECAR_IMAGE`, else `ankka-sidecar:latest` at version `0.0.0`, else
`ghcr.io/thinkmorestupidless/ankka-sidecar:<version>`.

**Decision**: the same kit in Go, in the package `testkit` of the one module. The DDL comes out of
the image through the Docker client testcontainers-go already depends on, not a shell, and goes in as
init scripts. The kit's API takes no `*testing.T`: `testkit.Start(ctx, service, opts...)` returns a
kit with `HTTP`, `Client`, `Storage`, `Restart`, `StartBeside` and `Stop`, and a convenience
`testkit.StartT(t, ...)` registers `Stop` with `t.Cleanup`; so it runs under `go test` and under any
other runner (FR-026). Slow tests skip unless `ANKKA_SLOW=1`, the switch the other SDKs use, so the
documentation can say the same words for every language; `go test -short` also skips them. The
component test kits are generic (`testkit.EventSourced(component)`) and reduce effects through the
same `materialise` functions the server uses.

**Alternatives considered**: a separate `testkit` module to keep Docker libraries out of a service's
module graph (rejected for now: Go downloads only the packages a build imports, a service that never
imports `testkit` fetches none of testcontainers' code, and a second module needs a second tag and a
version pin between the two; recorded as something to revisit if consumers object; V4 measures the
cost); a `-tags slow` build tag (rejected: an environment variable is what the other SDKs and the docs
use, and `-short` is honoured too).

## R8 — Publishing: a mirror repository, an immutable tag, the version from the build's own record

**Verified in this repository**: `release.yml`'s `template` job commits the version into the tree
on the runner, `git subtree split --prefix ankka.g8 -b ankka-g8`, force-pushes that branch to
`thinkmorestupidless/ankka.g8:main` with `secrets.TEMPLATE_REPO_TOKEN` in the URL (after
`actions/checkout` with `persist-credentials: false`, or the push goes as `github-actions[bot]`
and gets a 403), then `git tag -f v<version>` and force-pushes the tag; the `action` job does the
same for `ankka-action` and moves `v<major>` too. **Verified upstream** (go.dev module reference,
proxy.golang.org, sum.golang.org): the Go proxy fetches a version from the repository the first time
anyone asks and keeps it forever; the checksum database records the first content seen for a version
and every later `go get` verifies against it, so **a tag that moves after it was fetched breaks every
consumer with a checksum mismatch**; a version is withdrawn with a `retract` directive in a later
version's `go.mod`, never removed; a module in a subdirectory of a repository is tagged
`<dir>/vX.Y.Z`, a module at the root plainly `vX.Y.Z`; `debug.ReadBuildInfo()` lists every
dependency module with its `Version` as resolved (`v0.13.0` from the proxy; a `Replace` entry for a
`replace` directive; `(devel)` for the main module).

**Decision** (clarified in the spec): the release's `sdk-go` job splits `sdks/go` and pushes it to
`thinkmorestupidless/ankka-go`, module path `github.com/thinkmorestupidless/ankka-go`, tagged
`v<version>`, with the same token and checkout settings as the template job and **no `-f`**: the job
first asks the mirror whether the tag exists (`git ls-remote --tags`) and skips the push when it does,
the guard the npm and crates jobs have, because a Go tag must never move. Nothing in `sdks/go` is
rewritten by the job: the SDK has no version placeholder. `ankka.Version()` reads the build's record
and reports the `ankka-go` dependency's version without its `v` (so `0.13.0`, as the other SDKs
report), `0.0.0` for a `Replace` or when the SDK is the main module (its own tests and the examples in
this repository, whose `go.mod` files `replace` the module with `../..`), and that `0.0.0` is what
makes the test kit choose `ankka-sidecar:latest`, exactly the other SDKs' rule. The job's smoke test
then runs `go get github.com/thinkmorestupidless/ankka-go@v<version>` in an empty module against the
public proxy, with a few retries a minute apart because the proxy fetches lazily, builds a program
that prints `ankka.Version()`, and fails the job if it is not the tag's version. The mirror holds the
SDK's `README.md`, `LICENSE` (copied into `sdks/go` so the mirror carries one) and the examples; a
`retract` is added by hand in a later release if a version must be withdrawn. **One thing needs a
person before the first release**: the repository `thinkmorestupidless/ankka-go` must exist and
`TEMPLATE_REPO_TOKEN` must be allowed to push to it, as it is for the other three mirrors.

**Alternatives considered**: a nested module with `sdks/go/vX.Y.Z` tags (rejected at clarify); a
version placeholder rewritten by the job (rejected: the build's record already carries the truth,
and a rewritten `go.mod` is a different module hash than the tree's); a vanity import path
(rejected at clarify).

journal portability test starts the Scala cart image beside the Go cart on one Postgres, both ways.

## R11 — The storage client signs requests itself, as the other process SDKs do

**Verified in this repository**: `sdks/typescript/src/sigv4.ts` and `sdks/python/src/ankka/sigv4.py`
are hand-written SigV4 (header-signed and presigned) over the standard HTTP client; neither SDK
depends on an S3 library; the variables are `ANKKA_S3_{ENDPOINT,REGION,BUCKET,ACCESS_KEY,SECRET_KEY,
PUBLIC_ENDPOINT}`, per named bucket `ANKKA_S3_BUCKET_<NAME>`, `ANKKA_S3_EXPOSURE_<NAME>`,
`ANKKA_S3_PUBLIC_URL_<NAME>`, per supplied bucket the five with `_<NAME>`, `ANKKA_STORAGE_BACKEND`
(`s3|directory|memory`, chosen from the variables when unset), `ANKKA_STORAGE_DIR`
(`.ankka/storage`), and the directory store's address from `ANKKA_HTTP_INTERFACE` and
`ANKKA_HTTP_PORT`; the process serves `/_ankka/storage/<bucket|_default>/<name>` itself with `read`
and `keep` tokens, one GET and one PUT route per depth up to 16, declared only to a sidecar at 1.21
or later; `client.proto` says no rpc carries storage.

**Decision**: a port of the same design to Go over `net/http`, `crypto/hmac` and `crypto/sha256`:
the S3 store, the directory store with the `/_ankka/storage` endpoint, and the memory store the test
kit and the conformance runner use; the same variables; the same refusals of object names, proven by
the `storage/` fixture. The image uses a base with CA certificates (R13) so the S3 store can speak
TLS to a real endpoint.

## R13 — The image: a static executable in a distroless base

**Verified upstream**: `CGO_ENABLED=0 go build` yields a static executable for the standard
library's HTTP, TLS and SQL-free code paths; `gcr.io/distroless/static-debian12:nonroot` holds CA
certificates, a non-root user and nothing else (no shell, no package manager); `scratch` holds no CA
certificates. **Verified in this repository**: the TypeScript example's `Dockerfile` is `node:24-slim`
with `ENV ANKKA_PROCESS_PORT=9010`; the operator gives the app container no ports and no probe; the
process binds loopback inside the pod, whose network namespace the sidecar shares, so loopback is
right in the image too and the test kit alone needs the any-address binding.

**Decision**: a two-stage `Dockerfile`: `golang:1.27-alpine` builds with `CGO_ENABLED=0` and
`-trimpath -ldflags=-s -w`; the final stage is `gcr.io/distroless/static-debian12:nonroot` with the
one executable, `ENV ANKKA_PROCESS_PORT=9010` and `USER nonroot`. The template's and the example's
Dockerfiles are the same two stages; they differ only in the build context. The example's `go.mod`
replaces the SDK with `../..`, so its image is built by `examples/shopping-cart/scripts/image.sh`,
which stages `sdks/go` and the example into one temporary context and runs `docker build` there; the
template depends on the released module and is built from its own directory with no script. The new installing scenario ("no language runtime, no shell and
no package manager") is checked by the example's slow test inspecting the image's filesystem through
the Docker client.
