# Review: Design and build (061)

**Verdict:** Request changes
**What it does:** Adds a third spec-kit extension, `design-build`, whose two hand-rendered skills
(`/speckit-design` on `fable`, `/speckit-build` on `opus`) chain the existing stages from a
description to a draft pull request, plus two structural munit suites, a first Get started page, a
CI filter, living features, glossary terms and a trap in the testing rules.
**Should it exist:** yes, because the eight-step workflow and the model switch are currently held by
habit only. The extension packaging, the copy install and the `model:` frontmatter work around a
real renderer limit (R2, recorded as a trap). The design is sound, but three procedure defects below
break requirements the spec makes explicit.
**Read:** in full: both command files (and checked that their bodies match the skills), both
SKILL.md frontmatters, `extension.yml`, the extension README, both suites, the page,
`features/design-and-build/build.feature` and `models.feature`, the GLOSSARY hunk, the ci.yml,
mkdocs, index, extensions.yml and testing.md hunks, spec.md, plan.md, tasks.md,
`contracts/page.md`, and research.md's "Found during implementation". Skimmed: `design.feature`,
`installing.feature`, `features/documentation/design-and-build.feature`, the other spec artifacts
(data-model, contracts/extension, skills, stages, quickstart), and the two rendered skill copies
under `marketplace/` and `ankka.g8/` (generated by `just docs-sync`, held by `just docs`). Opened
outside the diff: `.claude/skills/speckit-specify`, `speckit-implement`, `speckit-analyze` and
`speckit-review` SKILL.md (the stages the new skills invoke), `.specify/extensions.yml`, the ci.yml
`unchecked` list, `ankka.g8/src/main/g8/` (for spec-kit), the sibling `*DocumentationSuite` classes.

## Blocking

- `.specify/extensions/design-build/commands/speckit.design.md:50` — issue (blocking): the
  default-branch guard never fires in a repository with a remote.
  `git symbolic-ref --short refs/remotes/origin/HEAD` prints `origin/main`, not `main` (verified in
  this worktree), so comparing it with `git branch --show-current` (`main`) never matches. Only the
  fallback to `main` makes the refusal work, and that fallback is taken only when there is no
  `origin/HEAD`. That is probably why the T010 scratch-repository run "refused on `main`". FR-015
  and the scenario "the design refuses to write a spec on the default branch" fail in every real
  checkout. Suggestion: strip the remote,
  `git symbolic-ref --short refs/remotes/origin/HEAD | sed 's|^origin/||'`, or use
  `gh repo view --json defaultBranchRef -q .defaultBranchRef.name`. Make the same change in the skill
  (the body-equality test enforces this). Then rerun the refusal in a clone that has `origin`.
  Resolved: the name is origin/HEAD with `origin/` taken off, or `main`; refusal rerun on `main` in a clone whose origin/HEAD is origin/main, refused, 896b07935

- `.specify/extensions/design-build/commands/speckit.build.md:119` — issue (blocking): the flake
  path cannot end correctly as written. Three lines interact:
  - Research T015 confirms that `gh pr checks --watch --fail-fast` exits 1 as soon as one check is
    red, while others are still pending.
  - Line 126 then says to cite the default branch's run and "count the check as passed". Nothing
    says to go on watching the checks that were still pending.
  - Watching "again" with `--fail-fast` exits at once on the same red flake. Line 139 also says
    "never mark the pull request ready while a check is red".

  So the agent either marks the pull request ready with checks still pending, which violates
  FR-022a, or loops, or stops. All three contradict the scenario "a red check the default branch
  also fails … does not hold the pull request". The spec carries the same contradiction: FR-022 lets
  a shown flake not hold the pull request, and FR-022a forbids ready "while any check is red". So
  the choice has to be made in the spec too.

  Suggestion: decide one rule in the spec and in the procedure. For example, after showing the
  evidence, rerun the failed job (`gh run rerun <id> --failed`), then watch without `--fail-fast`
  until every check has finished. Mark ready only when every check is green, or when every red check
  is one already shown to be a default-branch flake. Reword line 139 to match ("while a check is
  pending, or red without that evidence").
  Resolved: one rule in spec FR-022/FR-022a, contracts and the build: wait for checks to appear, `gh pr checks --watch` without `--fail-fast` until all finish, ready when each is green or a shown default-branch flake, 2476eee6b and 896b07935

- `.specify/extensions/design-build/commands/speckit.build.md:66` — issue (blocking): resuming
  can raise the pull request over a blocking finding the build disagreed with. The state table
  treats "every task `[X]`, `review.md` present" as *raising*. But `/speckit-review` has the
  reviewer write `review.md` before the findings are acted on, and stops on a blocking finding it
  disagrees with (speckit-review step 1). So after that stop, the next `/speckit-build` finds
  `review.md` present and goes straight to `gh pr create`. Today only the clean-tree precondition
  (line 54) gets in the way, and only while `review.md` is uncommitted. The scenario "a blocking
  finding the build disagrees with stops the build before the pull request" and FR-020 are lost
  across a restart. Suggestion: define "reviewed" as `review.md` with a `Resolved:`/`Declined:`/
  `Answered:`/`Left:` line under every finding. These are the resolution lines speckit-review's own
  checklist requires. Treat anything less as *reviewing*, which hands back to `/speckit-review`.
  Resolved: the review is finished only when every finding has a resolution line; otherwise the build returns to `/speckit-review` (FR-023a and a scenario), 2476eee6b and 896b07935

## Should fix

- `.specify/extensions/design-build/commands/speckit.build.md:72` — issue (non-blocking): the
  build has no counterpart to the design's question rule ("Hold this for every stage, including the
  stages' own instructions and their hooks"). The stages it invokes ask by ending the turn.
  `/speckit-implement` step 2 says "STOP and ask: 'Some checklists are incomplete. Do you want to
  proceed…' Wait for user response", and speckit-review "lets the user decide". This prompt is not
  among the four stop conditions of FR-020. If it is followed literally, it ends the turn, and the
  rest of the build runs on the session's model, which is the failure SC-001 exists to prevent.
  Suggestion: state the same rule once in the build body: every stage's own question goes through
  AskUserQuestion and never ends the turn. Also say what to do with implement's checklist prompt
  (for example: a design that passed analyze answers it "proceed", or ask through
  AskUserQuestion).
  Resolved: the build carries the question rule, implement's checklist question included, and in a headless session a stop condition ends the run saying what it would have asked, 896b07935

- `.specify/extensions/design-build/commands/speckit.build.md:101` — issue (non-blocking): the
  base rule requires the candidate's *head* commit to be an ancestor of this branch. If the base
  feature branch gained commits after this one was cut (a review fix, for example), its head is no
  longer an ancestor, the rule falls through to the default branch, and FR-021 is lost. That is the
  normal case for a stacked pull request still under review. Suggestion: test the merge base
  instead. A candidate qualifies when `git merge-base HEAD origin/<head>` is not an ancestor of the
  default branch. Pick the candidate whose merge base is newest. Pass `--limit` to `gh pr list`
  (its default is 30).
  Resolved: a candidate qualifies by its merge base with this branch not being on the default branch, newest merge base wins, `--limit 200`, 896b07935

- `.specify/extensions/design-build/commands/speckit.build.md:39` — suggestion: the build cannot
  tell an analysed task list from an unanalysed one. If a design stops after `tasks`, or after
  analyze's third round with "stop here", it leaves `tasks.md`. The build then implements it as if
  the design were finished, though the spec calls the build's input "an analysed task list".
  Suggestion: have the design record that it finished, for example the closing summary as a line in
  `research.md` or a marker in `tasks.md`. Have the build refuse without that record and name
  `/speckit-design --from analyze`.
  Resolved: the design appends `## Design finished` to research.md when analyze is done (not on "stop here"); the build refuses without it, naming `/speckit-design --from analyze` (FR-023 and a scenario); this feature's own research.md carries it, 2476eee6b and 896b07935
