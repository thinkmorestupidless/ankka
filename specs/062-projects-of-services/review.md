# Review: feature 062, projects of several services (origin/main...HEAD, 24 commits)

**Verdict:** Request changes
**What it does:** Adds a project of several services. The design skill decides one service or several and writes a context map. `core` gains `ContextMap` (it reads, checks and renders `context-map.json`) and `Names`, which takes over the control plane's name rules. The testkit gains `ContextMapCheck`, which holds the map to the topics a service's components declare. The CLI gains `ankka init --project` and `ankka init <service>` inside a project, plus `ankka context-map check|render`. A new project template has per-service tags, change-scoped CI and per-service deploys. The docs, the skills and the limitations page change to match.
**Should it exist:** Yes. The spec gives the reason: a group of services needs a recorded boundary, and each service needs to be released on its own. Nothing like this existed before. The control plane now reads its name rules from `core`, so the platform and a project's checks use one definition and do not repeat it.
**Read:** In full: `modules/core/.../ContextMap.scala`, `Names.scala`, `modules/testkit/.../ContextMapCheck.scala`, `cli/.../Projects.scala`, `ContextMapCommand.scala`, and the diffs of `Main.scala`, `Scaffold.scala`, `controlplane-api/.../descriptors.scala`, `DeclaredConnections.scala`, `build.sbt` and `.github/workflows/ci.yml`. ## Blocking

- `cli/src/main/scala/com/thinkmorestupidless/ankka/cli/Projects.scala:409` and `:416`; `cli/src/main/templates/project/scripts/run.sh:33-36`. Issue (blocking): every Python, TypeScript or Go service added inside a project gets the same fixed ports. Its sidecar dials `host.docker.internal:9010` and publishes `127.0.0.1:9011:9011`. `run.sh` starts the process without `ANKKA_PROCESS_PORT`, so the process takes the SDK default of 9010. A second process service therefore cannot run beside the first: its compose fails with the port already allocated, or its sidecar dials the first service's process. FR-017 asks that every service of a project run on one machine, and nothing in `docs/build/projects.md` or `limitations.md` mentions this. `addService` already chooses a free HTTP port and can choose the other two the same way.
  Suggestion: in `addService`, choose a process port and an observe port that no other service's compose uses (for example from 9010 in steps of 2, read back from `services/*/docker-compose.yml`). Write them into `sidecarCompose` as `ANKKA_PROCESS_ADDRESS` and the second `ports` entry. Have `run.sh` export `ANKKA_PROCESS_PORT` from the service's compose file (or from a small `.env` in its directory) before it starts the process. Extend `InitSuite`'s "next port" case to add two process services and assert their ports differ.
  Resolved: `addService` chooses the first free even port from 9010 for the process and the one above for the sidecar's observe port, chosen before the language's own compose file is written; `run.sh` exports `ANKKA_PROCESS_PORT` from the compose file; the README names the port; `docs/build/projects.md` says so. `InitSuite` adds a Python and a TypeScript service and reads both compose files (the case caught the template's own compose taking 9010), 5e0ef2eec.

- `modules/core/src/main/scala/com/thinkmorestupidless/ankka/core/ContextMap.scala:193-196` against `modules/runtime/.../DeclaredConnections.scala:129-135` and `modules/testkit/.../ContextMapCheck.scala:43-53`. Issue (blocking): a topic crossing from another project cannot be recorded in a way that passes both checks. The map invites crossings from `<project>/<service>`. A service reads another project's topic as `TopicAddress.of(name, project)`, which is `payments/ledger-events`, so `ContextMapCheck` compares that slash form with the crossing's `topic`. If the map records `"topic": "ledger-events"`, the run-time check reports both an unrecorded read and an unstated crossing. If it records `"payments/ledger-events"`, `ankka context-map check` refuses it as an invalid topic name. So any project that uses feature 040's cross-project topics has a red `ContextMapSuite` that no edit can fix. Today only a route is tested for an outside service (`ContextMapCheckSuite:189`).
  Suggestion: keep `topic` as the bare name in the map. In `ContextMap.topicCrossings`, or in `ContextMapCheck`, compare `TopicAddress.of(c.topic, projectOf(c.from))` for a read when `from` is `<project>/<service>` (and likewise `to` for a publication). Add a case to each of the two suites with a crossing from `payments/ledger` by a topic.
  Resolved: the map keeps the bare name; `ContextMapCheck` accepts either the bare name or `<project>/<name>` for a crossing with another project's service, in both directions, for the unrecorded, differing and unstated comparisons; the contract's ContextMapCheck section says so (Trevor approved the contract change). `ContextMapCheckSuite` gains a read from `payments/ledger` and a publication to it, over descriptors, 1305d3fe8.

- `deploy.yml`. Praise: `resolve` and `checks` run before any secret is read. The job declines rather than fails when `ANKKA_TOKEN` is absent, `ci.yml` names no secret, and the PR title reaches the shell only through `env`.
