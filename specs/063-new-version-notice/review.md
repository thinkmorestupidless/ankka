# Review: feat(063): a notice when a newer release exists

**Verdict:** Request changes
**What it does:** Each release's docs job writes `latest.json` beside the site. The CLI reads it in the background and prints one fixed line on stderr when a newer release exists, and `ankka mcp` carries the same notice in its instructions, `whoami`, `installation_status`, `search_docs` and `read_doc`. Pages that name an ankka release are rewritten to the release being built, for the site and for the pages the CLI carries, and `docs check` refuses a release written in any form the patterns file does not list.
**Should it exist:** yes. A model reading 0.13.0's pages through `ankka mcp` long after 0.16.0 shipped is a real, reported failure. One small static file read by both the CLI and the MCP server is the cheapest fix, and it adds no new dependency or service.
**Read:** in full: `cli/.../ReleaseCheck.scala`, `cli/.../mcp/ReleaseStatus.scala`, the diffs of `Main.scala`, `AnkkaTools.scala` and `McpServer.scala`, `project/ReleasePatterns.scala`, the `build.sbt` hunk, `tools/docs/src/ankka_docs/{release,hooks}.py` and the diffs of `cli.py`, `check.py`, `pages.py` and `render.py`, `ReleaseCheckSuite`, the `McpServerSuite` additions, `DocsBundleSuite`, `test_release.py`, both feature files, `docs/release-patterns.txt`, the diffs of `release.yml`, `ci.yml`, `.scalafmt.conf` and `native-smoke.sh`, every hand-edited `docs/` page, the three rule-file additions and `GLOSSARY.md`. Skimmed: the `ankka.g8/` and `marketplace/` copies of the pages, which are rendered from `docs/` by `docs sync`. Specs: `spec.md`, `plan.md`, `tasks.md`, `data-model.md`, `contracts/*`, and research R3 plus its "Found during implementation" section. Opened outside the diff: `mcp/Json.scala` (number round-trip in `withRelease`), `Main.parse`'s usage-error path (`--help` exits 2), and the `changes` filters in `ci.yml`.
**Size:** 157 files, +3359 −251. About 1300 of those lines are rendered skill copies and about 860 are spec documents, which leaves roughly 1700 hand-written lines (1150 Scala, 580 Python, the rest docs and CI). That is well past the point where reading finds defects reliably. A split I would accept: (a) the docs tool, patterns file and `latest.json` (US3 and US4); (b) the CLI and MCP notice (US1 and US2), which reads (a)'s file. Not blocking, since the work is already reviewed as one piece.

## Blocking
- `cli/src/main/scala/com/thinkmorestupidless/ankka/cli/ReleaseCheck.scala:245-266` — issue (blocking): a command that finishes before its background read never records anything, so the next command reads again. The only persisted timestamp is `checkedAt`, the last *successful* read, so there is no limit on attempts. For anyone whose commands usually beat the read, that means one request to docs.ankka.cloud per command, and no notice ever appears. That is most JVM-zip users of local commands: a cold JVM's TLS handshake to a public host takes hundreds of milliseconds, while `config get`, `local …` and `context-map check` return in milliseconds. The same happens on every command while offline. This breaks FR-005 ("MUST read the latest release at most once in 24 hours") and, for such a user, SC-001. The suite shows it rather than catching it: "a command ends when its own work ends" asserts `reads == 1` and nothing remembered, and a second run would read again. research.md "Found during implementation" records this as kept, but a spec MUST that fails for the common case needs fixing or an explicit spec change, not a note in the PR. Suggestion: persist an attempt before the read starts (add `attemptedAt: Option[Instant]` to `RememberedCheck`, and make `shouldRead` honour it at the same 24 h interval, or a shorter retry such as an hour for failed attempts). Also have the daemon thread `remember` its own result when it finishes, so a command that outlives the read keeps it even if `end` already ran. If SC-001 matters for fast commands, also allow a bounded wait at the end of `end`: SC-002 has a 100 ms budget for exactly this. Add a test that runs a fast command twice against a slow server and asserts `reads == 1`. Not run: the real-world timings above come from reading the code and the implementer's own note; I did not measure them.
  Resolved: `attemptedAt` written before each read, `shouldRead` honours a day after success and an hour after an attempt that did not succeed, the read thread remembers its own result, a command waits up to 100 ms (`Grace`); tests for two fast commands reading once, a stale attempt retried, a late read remembered by its thread, a read within the grace giving the notice; the retry rule mutated to zero goes red. FR-005 and FR-006 reworded with the person's choice recorded in spec.md's clarifications, 2fe43f4f0 and 835aec37d

## Should fix
- `cli/src/test/scala/com/thinkmorestupidless/ankka/cli/DocsBundleSuite.scala:55-68` — issue (non-blocking): on every pull request this suite can pass while the build's rewrite is broken. `docs sync` keeps the sources at the newest tag, and a development build's `release.txt` is `previousStableVersion`, the same tag. So between syncs the bundle already names that release with no rewrite at all, and a `build.sbt` that stopped calling `ReleasePatterns.rewrite` would stay green until the next tag's CLI build. Suggestion: add a case that cannot be satisfied by unchanged sources. Two options: a fixture page under `docs/` whose release form deliberately names an older tag, listed as something `docs sync` leaves alone (an `other`-style exemption is not right for this), or a unit test of `ReleasePatterns` from a `project/` test (`sbt reload plugins; test`). (if-minor)
  Resolved: `ReleasePatterns.bundle` is now the one function for the CLI's pages and a test fixture under `cli/src/test/release-fixture/` naming 0.1.0 in two release forms; a new case asserts the bundled fixture names the CLI's release, red when the rewrite is removed, 10cc2d28b
- `cli/src/main/scala/com/thinkmorestupidless/ankka/cli/ReleaseCheck.scala:164-171` — suggestion: each `read` builds an `HttpClient` and never closes it. On JDK 21 `HttpClient` is `AutoCloseable`, and each instance holds a selector thread until it is collected. In the CLI this is one per process, but `ReleaseStatus.tick` calls `read` every hour while a read is failing, for as long as the MCP server runs. Suggestion: `scala.util.Using.resource(HttpClient.newBuilder()...build())(client => ...)`, or a single lazily built client shared by both callers. (if-minor)
  Resolved: each read's `HttpClient` is closed through `Using.resource`, 2fe43f4f0
- `docs/release-patterns.txt:25` — suggestion: `release version={version}` is a very general literal. Every page is rewritten with it, so a future page showing another tool's `version=1.2.3` would be silently rewritten to ankka's release, and the check would not object because the occurrence is "covered". The same risk applies, less so, to `platform   {version}` and `{"version":"{version}"}`. Suggestion: make the install page's shell variable distinctive (`ankka_version=0.16.0`), so the pattern names only ankka.
  Resolved: the install page's variable is `ankka_version`, the pattern `release ankka_version={version}`; `platform   {version}` and `{"version":"{version}"}` stay, being the CLI's own output and `latest.json`, 8f31da02f

## Questions
- `cli/src/main/scala/com/thinkmorestupidless/ankka/cli/mcp/AnkkaTools.scala:43-47` — question: FR-014 says that when the latest release cannot be read, "every tool MUST answer as it does today". However, `whoami` and `installation_status` now always carry `release.cli`, and `installation_status` always carries `release.installation`, as `contracts/mcp-tools.md` says. The scenario's test compares the unreadable answer with the check-off answer, not with the pre-feature one. Is the contract meant to override FR-014's wording? If so, reword FR-014 ("adds nothing beyond `release.cli`") so the two documents agree.
  Answered: yes, the contract is meant. FR-014 now says the tools answer as they do with the check turned off, carrying only `release.cli` (and the installation's), 835aec37d
- `cli/src/main/scala/com/thinkmorestupidless/ankka/cli/ReleaseCheck.scala:145-153` — question: FR-008 says "when its error output is not a terminal". On JDK 21 the implementation actually tests whether stdin and stdout are terminals (R3). So `ankka … 2>log` in an interactive shell writes the notice into the log, and `ankka … | grep` stays silent. `docs/reference/cli.md` describes this accurately ("its output piped or redirected"). Should FR-008 be reworded to match what the CLI can detect?
  Answered: yes. FR-008 now says "not at a terminal (on JDK 21, standard input and output both the terminal; from JDK 22, the console is a terminal)", matching what the CLI can detect, 835aec37d
- `.github/workflows/release.yml:1010` — thought: `docs` needs only `publish`, so `latest.json` can announce a release before `cli-native`, `homebrew` and `action` have finished. For a short while, someone told "0.17.0 is available" who runs `brew upgrade` gets 0.16.0. This is consistent with FR-002, which names only the libraries, so no change is asked for. It is worth a line in the PR's notes.
  Answered: kept as it is (FR-002 names the libraries); noted in the pull request that `brew upgrade` may lag the notice by the minutes the release's later jobs take

## Praise
- `tools/docs/src/ankka_docs/release.py:200-201` and `test_a_checkout_without_the_tags_fails_the_check_rather_than_checking_nothing`: the check fails in a shallow clone instead of quietly checking nothing, with a message that names the fix, and both workflows gained `fetch-depth: 0`. This answers the repository's "could this pass while false?" question directly.
- `cli/src/test/scala/com/thinkmorestupidless/ankka/cli/McpServerSuite.scala` "the command line's MCP server gives the notice in its instructions": the 300 ms server delay makes the test fail unless `initialize` actually waits. That is a test written to be capable of failing.
- `tools/docs/src/ankka_docs/hooks.py` and `render.write(..., named)`: the build rewrites only the rendered site and never a source file, which keeps dynver's clean-tree rule (no dirty tree on a tag) out of reach.
- `cli/native-smoke.sh:150-178`: the native image's HTTP client, daemon thread and file write are tested on the binary itself, with a refused address on every build and the full path on a tag.

## Out of scope
- note: `docs/get-started/first-service-rust.md` dropped `version = "0.1.0"` from the example's `[package]`, apparently because `0.1.0` equals the `v0.1.0` tag and the check would refuse it. Cargo accepts the omission, but a check that pushes example projects away from ordinary versions will keep causing friction. Consider an issue on whether `tags` should be limited to releases from the supported compatibility window, rather than every tag back to v0.1.0.
